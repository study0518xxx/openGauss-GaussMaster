## Q1：为什么分块大小不固定？和 LangChain 固定 500 有什么区别？

**答**：项目用的是**自研 DNN 语义分块**，不是 LangChain 的固定大小切。

区别在于：

| | LangChain 固定 500 | 自研 DNN 语义分块 |
|---|---|---|
| 块大小 | 固定 500 ± 50 | **可变**，取决于语义完整性 |
| 代码块 | 可能被切断 | **保护不切** |
| 表格 | 可能从中间断开 | **完整保留** |
| 元信息 | 无 | 每块标注版本号、前后块 UUID |
| 去重 | 无 | 文本哈希全局去重 |

实际效果：一个 30 行的 SQL 示例（200 字）单独成块，不会被 LangChain 硬凑到 500 字拼上不相关的内容；一个 800 字的长段落也不会硬切成两半。**语义完整性优先于字数的均匀性。**

**追问：这么做检索的时候有什么好处？**  
LLM 看到的每块都是一个完整的知识点——不是半截 SQL、不是零散句子。检索精度更高，答案质量更好。代价是分块逻辑更复杂，776 行代码。

## Q2：自研分块器和 LangChain 哪个好？为什么不用现成的？

**答**：LangChain 的 `RecursiveCharacterTextSplitter` 是好的通用方案，但我们的场景有三个特殊需求它不支持：

1. **代码块和表格不能切**。数据库文档里有大量 SQL 示例和参数表格，从中间断开 LLM 看到的就是语法错误的 SQL，严重时给出错误建议。自研分块器识别 ` ``` ` 和 `|--|` 标记，跨越这些内容时自动延长块。

2. **元信息增强**。每块除了文本内容，还要标注它来自哪个文档、哪个版本、前后块的 UUID。检索时如果相邻两块都命中，可以通过前后块 UUID 串起来还原完整上下文。

3. **全局去重**。多个文档里可能存在相同段落（比如不同版本文档的公共章节），不出去重的话检索结果里会出现完全一样的块，浪费 LLM 上下文窗口。

LangChain 做不了这三件事，所以自研了 776 行的 `split_util_md.py`。**不是 LangChain 不好，是通用框架满足不了领域特定需求。**

## Q3：为什么选 BGE-large-zh，还做了微调？

**答**：分两步——

**选型**：BGE-large-zh 是智源研究院的模型，C-MTEB 中文基准测试排名前三。和 BGE-small（512 维）、text2vec（1024 维）对比过，在数据库运维领域的短文本检索上 BGE-large 明显更好——因为数据库术语多，"CPU 使用率"、"shared_buffers"、"pg_stat_activity" 这些专业词，大模型区分得更精细。

**微调**：通用嵌入模型没见过 GaussDB 的专有名词。比如 "GSDiskANN"、"gs_ctl"、"floatvector"——这些词在通用语料里几乎没有。我们用 **10.6 万条 GaussDB 产品文档和排障案例**做了微调，让模型知道 "GSDiskANN" 和 "磁盘向量索引" 是高度相关的，"gs_ctl build" 和 "备机重建" 是同一个意思。

微调后检索命中率提升了约 15%，在银行场景的 1614 个真实问题上效果好于通用版 BGE。

## Q4：1024 维能调吗？为什么是 1024 不是别的？

**答**：维度是 BGE-large 的模型结构决定的——输出层大小固定 1024，`get_embedding_dimensions()` 硬编码返回 1024，不是可调参数。

如果要降维，可以做 **PCA 后处理**或换 BGE-small（512 维），但精度会下降。生产环境选择不降——因为：

- GSDiskANN 支持 PQ（乘积量化）压缩，1024 维向量压缩后内存占用接近 256 维
- 1024 维 L2 距离计算在 GSDiskANN 索引加持下，百万级向量搜索仍能做到毫秒级
- 微调后的模型 1024 维已经是最优配置，降维损失不值得

**追问：那 OpenAI text-embedding-3 可以调维度，为什么不用？**  
那是付费 API，银行内网环境没法调外部服务。而且 text-embedding-3 没在 GaussDB 语料上微调过，效果不如自训练的 BGE。

## Q5：为什么用 openGauss 做向量数据库，而不是 Milvus / Chroma？

**答**：这是面试里最容易被追问的点。三个原因：

**1. 一张表搞定混合检索。** openGauss 是 PostgreSQL 兼容的，一张表可以同时有：
- `text` 字段 — 存文档原文
- `text_vector floatvector(1024)` — 存 1024 维向量
- BM25 全文索引 — 存关键词倒排

向量检索 + 关键词检索在同一张表上完成，不需要跨系统。如果换成 Milvus + Elasticsearch，数据要同步两份，一致性难保证。

**2. GSDiskANN 磁盘索引。** 银行场景知识库百万级文档块，全内存索引放不下。GSDiskANN 是 openGauss 自研的磁盘向量索引——参考 Microsoft DiskANN 算法，支持 PQ 压缩，内存占用只有全量向量的几十分之一。Milvus 的 HNSW 是纯内存索引，数据量大时成本高。

**3. 部署简单。** 银行客户已经部署了 openGauss 数据库，不需要额外引入一个新组件。数据库运维团队对 openGauss 熟悉，出问题能自己排查，不用学新的技术栈。

## Q6：GSDiskANN 和 HNSW 有什么区别？

**答**：

| | HNSW | GSDiskANN |
|---|---|---|
| 索引位置 | **内存** | **磁盘 + 内存缓存** |
| 数据量 | 适合百万以下 | 适合**百万到十亿** |
| 内存占用 | 全量向量 + 图结构 | PQ 压缩，压缩比 8:1~16:1 |
| 搜索精度 | 99.5%+ | 95%+（可调） |
| 部署 | 独立服务（Milvus/Chroma） | openGauss 内核插件 |

创建索引的 SQL：

```sql
CREATE INDEX ON gauss_kb
USING gsdiskann(text_vector l2)
WITH (
    pq_nseg=1024,      -- PQ 段数，等于维度数
    pq_nclus=16,       -- 聚类数，越大精度越高内存越大
    queue_size=100,    -- 搜索队列大小
    num_parallels=30,  -- 并行度
    enable_pq=true     -- 开启乘积量化压缩
);
```

**为什么选磁盘索引**：银行场景知识库百万级文档块，单条 1024 维 float32 向量 = 4KB，100 万条 = 4GB。HNSW 图结构还会额外占 2-3 倍内存——总需求 10GB+。PQ 压缩后降到 ~500MB，内存成本可控。

## Q7：混合检索（向量 + BM25）具体怎么做的？

**答**：三阶段——

```
用户问题: "GaussDB CPU 使用率飙高怎么排查"
  │
  ├─ 阶段1: 向量检索（语义匹配）
  │    ORDER BY text_vector <-> query_vector LIMIT 10
  │    → 找到语义相似的块（"CPU占用过高诊断"、"处理器负载排查"）
  │
  ├─ 阶段2: BM25 全文检索（关键词匹配，兜底）
  │    ORDER BY text ### 'GaussDB CPU 使用率飙高' DESC LIMIT 10
  │    → 找到含有 "CPU"、"使用率"、"飙高" 关键词的块
  │
  └─ 阶段3: BGE-reranker 重排序
       把两路结果合并去重 → 用微调的 BGE-reranker 打分
       → 过滤 score < 0 的 → 取 Top-3 送 LLM
```

**为什么两路都要**：向量擅长 "CPU 飙高" ≈ "处理器占用异常" 这种语义匹配，但遇到代码级别的精确匹配会漏（比如搜 "pg_stat_activity"，向量可能软匹配到 "pg_stat_user_tables"——名字像但其实不同）。BM25 做关键词精确兜底，保证术语不会被语义"模糊化"。

---

## Q8：BGE-reranker 在哪个环节？score < 0 过滤是什么意思？

**答**：两路检索各返回 Top-10，合并去重后大约 15-18 个候选块。这 15 个块都要送 LLM 的话太多了——3 个就够。reranker 的任务是**对候选块重新打分排序**。

和 embedding 检索的区别：
- Embedding 是**独立打分**——每个块单独和查询向量算距离
- Reranker 是**交叉打分**——查询和候选块拼成一对 `[query, doc]` 一起送模型，模型判断 "这段真的能回答这个问题吗"

rerenker 输出的分数范围是 -1 到 +1：

```
score > 0.5  → "高度相关" ✅
score 0~0.5  → "弱相关"   ⚠️ 保留但排后面
score < 0    → "不相关"   ❌ 直接丢弃
```

`score < 0` 过滤就是把 reranker 判定为"不相关"的块去掉。这一步很关键——embedding 检索可能会把 "连接数过多" 这个块排进 CPU 问题的 Top-10（因为都涉及性能），但 reranker 交叉比对后会判定 < 0，过滤掉。

## Q9：HyDE + 查询改写降级策略怎么工作的？

**答**：当混合检索 + 重排序后仍然无结果（所有候选都被过滤），不直接返回 "不知道"，而是做两步抢救：

**1. HyDE（假设文档嵌入）**

让 LLM 自己编一个假设答案，用这个答案去检索：

```
用户: "备机重建失败怎么处理"
  → 检索无结果
  → LLM 编一个假设答案: "备机重建失败可能是因为网络中断、WAL日志不连续、
     或者 gs_ctl build 命令参数错误……"
  → 用这个假设答案做向量化 → 重新检索
  → 假设答案里含有关键词 "gs_ctl build"、"WAL" → 帮助匹配
```

原理：用户问题可能很短、术语不规范。LLM 生成的假设答案更长、术语更规范——用它做向量检索命中率更高。

**2. 查询改写**

如果 HyDE 也不行，让 LLM 把原始问题拆成 3 个子问题分别检索：

```
原始: "备机重建失败怎么处理"
  → 子问题1: "gs_ctl build 命令报错怎么办"
  → 子问题2: "WAL 日志同步失败如何恢复"
  → 子问题3: "备机重建流程和注意事项"
```

拆成小问题后每个都更容易匹配到具体文档。拆开检索 + 合并结果，比单次检索召回率高。

这两步降级策略将空结果概率降低了约 40%。

## Q10：用 L2 距离还是余弦距离？阈值设多少？

**答**：用 **L2 距离**（`<->` 操作符），阈值 `l2_distance_threshold = 0.9`。

```python
# gaussdb_vector.py
distance_strategy = "l2"

# 配置文件
l2_distance_threshold = 0.9
```

L2 和余弦的选择：向量做了归一化后两者等价（见 Q5 的数学推导）。选 L2 纯粹因为 openGauss 的 `<->` 操作符就是 L2 距离，GSDiskANN 也是按 L2 建的索引。

阈值 0.9 的设定来自**在生产数据上跑出来的经验值**：1614 个银行真实问题里，L2 距离 > 0.9 的结果几乎全部是噪声，< 0.9 的结果里有 85%+ 是真正相关的。所以把 0.9 作为过滤线。

## Q11：为什么用 HTTP 嵌入服务而不是本地加载模型？

**答**：

1. **多服务共享**。系统里有多个模块需要向量化——知识库入库、RAG 检索、工具历史记忆搜索。如果每个服务各自加载一个 1.3GB 的 BGE 模型，内存浪费严重。HTTP 服务部署一个实例，所有模块调它。

2. **微调模型管理**。微调后的模型更新频繁（新文档批次微调），HTTP 服务可以热切换模型版本，不用改代码重启。

3. **独立扩缩容**。嵌入服务是 CPU 密集型，Web 服务是 IO 密集型。HTTP 分离部署后可以各自按需扩容——高峰期嵌入服务多加几个实例，Web 服务保持不变。

## Q12：怎么验证检索效果？和普通 RAG 项目差在哪？

**答**：

**验证方式**：
1. 银行提供了 1614 个真实 QA 问题，人工标注了正确答案对应哪些文档块
2. 跑一轮检索，算两个指标：**Recall@3**（正确答案在 Top-3 里出现的比例）和 **MRR**（正确答案排第几）
3. 对比不同配置：只用向量 vs 只用 BM25 vs 混合、有无 reranker、有无 HyDE 降级

**和普通 RAG 项目的差异**：

| | 普通 RAG 项目 | GaussMaster |
|---|---|---|
| 检索方式 | 单路向量 | **向量 + BM25 双路混合** |
| 向量数据库 | Chroma / Milvus / Pinecone | **openGauss 自身**（floatvector + GSDiskANN） |
| 索引 | HNSW 内存 | **GSDiskANN 磁盘**（百万级，PQ 压缩） |
| 分块 | LangChain 固定 500 | **自研 DNN 语义分块**（代码块/表格保护） |
| 重排序 | 无或简单的 score 排序 | **BGE-reranker 微调版**，score < 0 过滤 |
| 降级 | 无结果就返回 "不知道" | **HyDE + 查询改写**两级降级 |
| 嵌入模型 | 通用版 BGE | **微调版 BGE**（10.6 万 GaussDB 语料） |
| 安全 | 无 | **DFA 敏感词 + XLNet** 双层 |

**落地效果**：QA 回答高质量率 85.23%，34 个运维场景零人工干预。
