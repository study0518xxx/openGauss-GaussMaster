# GaussMaster 工具调用（Tool / Function Calling）——面试 5 步法完整版

---

## 开场：这个系统在干什么

> ① 我们需要让 LLM 能调数据库诊断工具——用户说 "帮我查一下 CPU"，系统要自动调 `get_cpu_usage` 这个函数。② 业界标准做法是用原生 Function Call API——OpenAI 有、盘古也有。但问题是我们支持 6 种模型，每个的 Function Call 格式都不一样——盘古的 `function_call` 字段叫一个名字，ChatGLM 根本没有这个能力。③ 所以我设计了一套模型无关的两阶段方案：阶段一让 LLM 从 21 个工具里选名字，阶段二把工具 schema 给它填参数，输出 JSON 后代码做确定性校验。④ 为什么不用 LangChain AgentExecutor——它的 ReAct 循环让 LLM 自由选工具，在数据库诊断场景会跳过关键步骤。⑤ 准确率从一步到位的 60% 提到两阶段的 95%+，在银行 1614 个真实问题上验证的。

---

## 模块一：工具注册表（Registry）

> ① 21 个工具需要一个统一的管理方式。② 如果每个工具散落在不同文件里，加新工具要改好多地方。③ 我用装饰器模式做了一个 Registry——`@base_tools(name="get_cpu_usage", description="获取 CPU 使用率", params=[Param("instance", "实例名", "str", required=True)])`，一行装饰器就注册完了。Param 类定义了参数契约：名字、类型、是否必填、默认值。④ 为什么要用装饰器而不是配置文件——配置文件只能描述元数据，装饰器直接绑在函数上，函数签名和参数定义天然对应，`inspect.signature` 校验时不用额外维护两套信息。⑤ 21 个工具都通过同一套 Registry 管理，加新工具只加一个函数 + 一个装饰器，零侵入。

---

## 模块二：为什么两阶段

> ① 我需要 LLM 从 21 个工具里选一个，并且填上正确参数。② 如果一步到位——让 LLM 一次性从 21 个工具 × 平均 3 个参数 = 63 维里找答案——盘古实测准确率只有 60%。③ 我把这 63 维拆成两步：先做 21 维的 "分类"（选工具名），再做 3 维的 "提取"（填参数）。④ 为什么有效——这不是技巧，是数学。分治把高维搜索拆成两个低维步骤，每一步 LLM 犯错概率的乘积远小于一步犯错概率。就像让你从 63 个号码里猜一个数，和先猜 1-21 再猜 1-3——后者每一步都比前者简单十倍。⑤ 拆开后准确率 95%+。ChatGLM、百川这些不支持 function_call 的模型也能用——它们只需要输出文字，不需要原生 API。

---

## 模块三：两阶段具体怎么做

### 阶段一：选工具

> ① 把 21 个工具的名字和一句话描述拼成文本。② 如果不加约束，LLM 会输出 "我建议使用 get_cpu_usage 工具来查询……"——多了一堆废话。③ prompt 里明确写 "只输出工具名称，不要输出其他任何内容"。LLM 返回 `get_cpu_usage`——裸字符串。然后 `Registry.get(tool_name)` 查字典校验是否存在。④ 为什么不用 JSON 格式——选工具这一步只需要一个名字，JSON 反而增加 LLM 输出错误的概率（少一个引号就解析失败）。一个字都不用解析。⑤ 21 个工具，选错率 < 5%。

### 阶段二：填参数

> ① 把选中工具的完整 schema 给 LLM：参数名、类型、是否必填、说明。② 不加约束 LLM 可能输出 `{"instance": "db_001", "hack": "DROP"}`——多编了不存在的参数。③ prompt 里给示例 `{"instance": "db_001"}`，只输出 JSON。LLM 返回后 `json.loads` 解析，再用 `verify_arguments()` 校验——多的参数丢弃，缺的必填参数提示用户补充。④ 为什么不用 prompt 约束就够了——prompt 是 99%，代码校验是 100%。生产环境那 1% 的误操作是不可接受的。比如 LLM 幻觉了一个 `force=True` 参数，如果直接执行可能强制重启数据库——代码层直接 `pop` 掉。⑤ 参数填充准确率 99%+，多给参数自动丢弃，零安全隐患。

---

## 模块四：无参数工具快捷路径

> ① 有些工具不需要参数——比如 `get_connections` 直接返回当前连接数。② 如果还是走完整两阶段，LLM 看到 "参数列表为空" 可能输出空 JSON `{}` 或者 "无参数"——浪费一次 LLM 调用。③ `check_is_no_param_tool()` 判断参数列表为空时，直接跳过阶段二，调 `call_tool(tool_name, {})`。④ 为什么麻烦做这个判断——每次 LLM 调用都是一次网络请求 + API 费用。一个快捷路径省下的累积起来很可观。⑤ 省一次 LLM 调用，回答延迟减少 500ms-1s。

---

## 模块五：参数校验的确定性

> ① LLM 输出的参数未必安全——可能多编、可能缺必填项。② 如果靠 prompt 约束——"请只输出需要的参数"——LLM 可能不听，也可能会漏。③ `verify_arguments()` 用 `inspect.signature` 拿到函数真实的参数签名，和 LLM 给的参数逐一比对：名字不匹配的直接丢弃，必填参数缺的标记出来。④ 为什么不用 LangChain 的 OutputParser——它也是靠 prompt 约束，没有真正的 "校验" 步骤。我的做法是把校验和 prompt 解耦——prompt 负责引导，代码负责把关。prompt 是软约束，代码是硬约束。⑤ 校验层正确率 100%，零漏过。银行场景不能接受 "AI 乱调了一个参数"。

---

## 模块六：会话状态——为什么记两样东西

> ① 用户和一个工具可能有多轮交互——第一轮选了工具但缺参数，第二轮用户补充参数，系统需要知道 "上次选的什么工具"。② 如果不记状态，第二轮用户说 "48 小时"，LLM 得从 21 个工具里重新猜——大概率猜错。③ 记两样东西：`SESSION_TOOL_HISTORY` 记 "当前正在调哪个工具"（一个字符串），`SESSION_QA_HISTORY` 记 "刚才聊了什么"（完整对话记录）。前者防重复选工具，后者注入 LLM prompt 做多轮上下文。④ 为什么分两个结构——一个只需要一个值，快速查；一个需要多条记录，用于 prompt 拼装。混在一起反而都慢。⑤ 第二轮用户补充参数时，LLM 调用次数从 2 次减到 1 次，延迟减半。

---

## 模块七：多模型适配——盘古和 ChatGLM 怎么走同一条路

> ① 6 种模型的 LLM API 各不相同——盘古有 `function_call` 字段，ChatGLM 只能输出纯文本。② 如果给每种模型写一套工具调用逻辑，6 套代码维护成本爆炸。③ 统一接口：`BaseLLM.invoke(prompt) → (content, function_call_dict)`。盘古返回 `("文字", {"name":"get_cpu_usage","arguments":...})`，ChatGLM 返回 `("get_cpu_usage", None)`。上层只判断 `if func_call is not None` 走不同解析路径——之后全部复用。④ 为什么不用适配器模式强行统一——DeepSeek 和 Qwen 是 OpenAI 兼容 API，直接 HTTP POST 比套一层适配器更简单。两条路径（LLM 类路径 + 通用 HTTP 路径）各管各的，不强求统一。⑤ 换模型只改配置文件的 `api_type`，业务代码 0 行改动。

---

## 收尾：完整的 9 步从入口到落库

> ① 用户请求进来 → ② 查缓存（上次选的工具还在吗？）→ ③ 读对话历史 → ④ LLM 选工具 → ⑤ Registry 检验 → ⑥ 无参数？直接执行 → ⑦ LLM 填参数 → ⑧ `verify_arguments` 校验 → ⑨ 执行 + 双写记录。④⑤⑥⑦ 这四步是核心——选工具、验工具、填参数、验参数。每一步都有 "为什么不做别的选择"。最终效果：选工具准确率 95%+，填参数 99%+，校验 100%。银行 34 个运维场景零人工干预。
