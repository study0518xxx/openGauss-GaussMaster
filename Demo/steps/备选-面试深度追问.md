## 一、PQ 压缩（乘积量化）

### Q：PQ 压缩 8:1 ~ 16:1 是什么？

**答**：PQ（Product Quantization，乘积量化）是一种有损向量压缩算法，用于降低向量索引的内存占用。

**原理**：

把 1024 维向量拆成若干段，每段用最近的一个"聚类中心编号"代替原始浮点数：

```
原始向量（每条 4096 bytes）:
  [0.12, -0.34, 0.56, 0.78, -0.23, ...]  ← 1024 个 float32（每个 4 bytes）

PQ 压缩后（每条 512 bytes）:
  拆成 1024 段（每段 1 维），每段量化到 16 个聚类中心之一
  → 每段只存 4 bits 的聚类编号
  → 1024 × 4 bits = 512 bytes

压缩比: 4096 / 512 = 8:1（仅向量部分）
        加上码本共享、元数据压缩 → 整体 12:1 ~ 16:1
```

**GaussMaster 的配置**：

```sql
CREATE INDEX ON gauss_kb USING gsdiskann(text_vector l2)
WITH (
    pq_nseg=1024,     -- 分 1024 段，每段 1 维
    pq_nclus=16,      -- 每段 16 个聚类中心（4 bits 编码）
    enable_pq=true
);
```

**精度代价**：搜索精度从 99.5% 降到 95%+，但百万级内存从 10GB+ 降到 ~2GB，数据库运维场景够用。

**类比**：一张高清照片（float32）→ 换成 16 色调色板（4 bits 聚类编号）。看起来略有损失，但一眼还能认出是什么。

## 二、GSDiskANN 部署方式

### Q：GSDiskANN 怎么部署？是独立中间件吗？

**答**：不是独立中间件。GSDiskANN 是 openGauss 数据库内核自带的索引引擎，和 B-Tree 索引一样用法。

**部署流程**：

```
1. 安装 openGauss 数据库
   → GSDiskANN 随内核一起安装，无需单独操作

2. 建表
   CREATE TABLE gauss_kb (
       uuid TEXT,
       text TEXT,
       text_vector floatvector(1024)   -- openGauss 扩展的向量列类型
   );

3. 建索引（一行 SQL，和建 B-Tree 一样简单）
   CREATE INDEX ON gauss_kb
   USING gsdiskann(text_vector l2)
   WITH (pq_nseg=1024, pq_nclus=16, queue_size=100,
         num_parallels=30, enable_pq=true);

4. 检索（用 <-> L2 距离操作符）
   SELECT * FROM gauss_kb
   ORDER BY text_vector <-> '[0.12, -0.34, ...]'
   LIMIT 10;
```

**GaussMaster 怎么用**：

```python
# common/metadatabase/dao/gaussdb_vector.py
class GaussDB:
    def __init__(self, db_config):
        # psycopg2 连 openGauss，和连 PostgreSQL 一样
        self.conn = psycopg2.connect(
            host=db_config['host'],
            port=db_config['port'],
            dbname=db_config['dbname']
        )

    def _create_index_vector(self):
        # 建索引就是一条 SQL
        self.cur.execute(f'''
            CREATE INDEX ON "{table}"
            USING gsdiskann("{key}_vector" l2)
            WITH (pq_nseg=1024, pq_nclus=16, ...)
        ''')
```

**面试表述**：

> GSDiskANN 不是独立服务——它就是 openGauss 的一个索引类型。和建 B-Tree 索引一样，`CREATE INDEX ... USING gsdiskann` 一行 SQL 搞定。应用层用 psycopg2 连 openGauss，检索用 `<->` L2 距离操作符。部署上是零额外成本的——客户已经装了 openGauss，不需要再部署 Milvus 或 Elasticsearch。

## 三、BM25 全文索引

### Q：BM25 是什么？怎么和向量检索配合？

**答**：BM25 是经典的文本检索排序算法，基于词频（TF）和逆文档频率（IDF）打分。

**为什么和向量一起用**：

| 场景 | 向量检索 | BM25 |
|------|---------|------|
| "CPU 飙高" ≈ "处理器占用异常" | ✅ 语义匹配成功 | ❌ 没有共同关键词 |
| "pg_stat_activity 怎么用" | ⚠️ 可能模糊匹配到 pg_stat_user_tables | ✅ 精确命中关键词 |

两路互补——向量覆盖语义变体，BM25 覆盖精确术语。

**配置**：

```sql
CREATE INDEX ON gauss_kb USING bm25(text) WITH (num_parallels=30);

-- 检索
SELECT * FROM gauss_kb
ORDER BY text ### 'CPU 使用率飙高' DESC
LIMIT 10;
```

`###` 是 openGauss 的 BM25 排序操作符。

## 四、微调嵌入模型

### Q：BGE-large 微调用的什么数据？怎么微调的？

**答**：用 **10.6 万条 GaussDB 产品文档和排障案例**做领域微调。

**为什么微调**：通用 BGE 不认识 GaussDB 的专有名词——"GSDiskANN"、"gs_ctl"、"floatvector" 在通用语料里几乎没有。微调后模型知道：
- "GSDiskANN" ≈ "磁盘向量索引"
- "gs_ctl build" ≈ "备机重建"
- "floatvector(1024)" ≈ "向量列类型"

**效果**：在 1614 个银行真实问题上，微调版比通用版检索命中率提升约 15%。

**部署**：微调后的模型部署为 HTTP 嵌入服务（`OnlineEmbedding`），多模块共享调用。模型更新时热切换，不用改代码重启。

## 五、安全检测细节

### Q：DFA + XLNet 双层安全怎么工作的？

**答**：

**第一层 DFA（显式检测）**：
- Trie 树存储 2 万多条敏感词/危险命令
- 输入文本逐字匹配，O(n) 时间复杂度
- 命中即拦截："DROP TABLE"、"rm -rf"、"shutdown" 等

**第二层 XLNet（隐式检测）**：
- 微调 XLNet 做文本风险二分类
- 检测不含敏感词但意图危险的输入，比如"帮我把生产库重建一下"
- 推理时间 < 500ms
- 输入和 LLM 输出两端都过检测

**为什么两层**：DFA 快但只认识词表里的，XLNet 能理解语义但慢一些。DFA 先快速过滤显式攻击，XLNet 再拦截隐式风险。输出也要过——防止 LLM 被 jailbreak 后生成危险内容。
