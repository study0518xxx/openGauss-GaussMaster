**项目时间**：2024 年 6 月 - 至今 | **角色**：核心开发者

**项目概述**：基于大语言模型的 openGauss 数据库智能运维系统，覆盖知识问答、故障诊断、性能调优全生命周期。通过自然语言即可完成数据库运维操作，34 个运维场景实现零人工干预，QA 回答高质量率 85.23%，工具调用准确率 95%+。已在中国农业银行生产环境部署，相关论文发表于 arXiv（2506.23322）。

**个人职责与成果**：

- **设计并实现了 RAG 混合检索管道**。自研向量检索（openGauss GSDiskANN 磁盘索引）+ BM25 全文检索双路混合，配合微调 BGE-reranker 重排序过滤。设计了 HyDE（假设文档嵌入）+ 查询改写的两级降级策略，将检索空结果概率降低约 40%。知识库采用自研 DNN 语义分块，保护代码块和表格不被切割。

- **搭建了完整的 Web 服务与安全体系**。FastAPI + Uvicorn 实现核心路由，SSE 流式输出（`text/event-stream` + `keep-alive`）。设计 DFA 敏感词检测（Trie 树，2 万+词库）+ 微调 XLNet 模型（<500ms）双层安全检测，同时应用于输入和输出。

- **实现了多轮对话记忆与多 Agent 协同诊断**。3 轮滑动窗口对话记忆，历史上下文注入 LLM prompt。设计诊断树引导的确定性 Agent 路径，替代 LangChain/LangGraph 的自由探索模式，在 34 个根因场景中稳定性显著优于通用 Agent 方案。

**技术栈**：Python、FastAPI、Uvicorn、openGauss、GSDiskANN、BM25、psycopg2、BGE-large-zh（微调）、BGE-reranker（微调）、盘古 / DeepSeek、XLNet、asyncio

## 二、面试时怎么说 — 完整话术

### 2.1 一句话介绍（10 秒版）

> "我做的是一个基于大语言模型的数据库智能运维系统，用自然语言对话完成数据库的问答、诊断和调优，已经在银行 34 个场景实现零人工干预。"

### 2.2 项目概述（1 分钟版）

> 这个项目叫 GaussMaster，核心思路是用大语言模型充当 DBA 的 Copilot。数据库运维门槛很高——一个 DBA 需要熟读上千页产品文档，遇到告警可能要翻半小时手册才能确定方向。我们的系统让运维人员直接用自然语言提问，比如"CPU 使用率过高怎么办"或者"帮我查一下慢 SQL"，系统自动检索知识或调工具执行，然后给出答案。
>
> 整个系统分三层——知识层用 openGauss 自带的 GSDiskANN 向量索引加 BM25 全文索引做混合检索，推理层用自研的两阶段 Agent 管道做工具编排，执行层通过 DBMind 平台纳管 21 个数据库诊断工具。我负责推理层的核心设计和实现。项目已经在银行生产环境落地，34 个运维场景零人工干预。

**每个环节怎么讲：**

**1. 文档分块和向量化**

> 首先要把产品文档变成系统能理解的知识。我们没用 LangChain 的固定大小切块——数据库文档里有大量 SQL 代码和参数表格，固定 500 字切会把 SQL 从中间断开。自研了 DNN 语义分块器，保护代码块和表格不被切割，每块大小不固定、取决于语义完整性。每块还标注了版本号、前后块 UUID 做元信息增强。然后全量文本哈希去重。
>
> 向量化用的是 BGE-large-zh，在 10.6 万条 GaussDB 语料上做了微调，1024 维。微调后数据库专有名词（比如 "GSDiskANN"、"gs_ctl build"）的检索命中率提升了约 15%。

**2. 混合检索管道**

> 检索不是单路向量。我们做了向量 + BM25 双路混合——向量做语义匹配（"CPU 飙高" ≈ "处理器占用异常"），BM25 做关键词兜底（精确匹配术语，不会被语义"模糊化"）。两路各取 Top-10，合并去重后送 BGE-reranker 重排序。
>
> reranker 是微调过的，交叉打分后过滤 score < 0 的块——确保送 LLM 的每块都真正相关。如果过滤后没有结果，启动 HyDE 降级——让 LLM 编一个假设答案，用这个答案重新检索——或者查询改写，把问题拆成 3 个子问题分别搜。两级降级把空结果概率降低了约 40%。
>
> 向量数据库用的是 openGauss 自身，不是 Milvus 或 Chroma。openGauss 是 PostgreSQL 兼容的，一张表同时支持 floatvector 向量列和 BM25 全文索引。索引用的是 GSDiskANN——openGauss 的磁盘向量索引，基于 Microsoft DiskANN，支持 PQ 压缩。百万级文档块内存只占 500MB。

**3. SSE 流式输出**

> 回答用 SSE 流式——不是等 LLM 全生成完再返回。FastAPI 的 StreamingResponse 设 `text/event-stream` + `keep-alive` + `no-cache`。两层 stream：LLM API 端 stream=True 逐 token 收，FastAPI 端 StreamingResponse 逐 chunk 推。

**4. 两阶段工具调用**

> Agent 工具调用是整个系统最有技术含量的部分。业界通常用 LLM 的原生 Function Call API——但我们系统要支持盘古、DeepSeek、ChatGLM 等 6 种模型，每个模型的 Function Call 格式都不一样。我做了一个模型无关的两阶段方案：
>
> - 阶段一：把 21 个工具的名字和描述拼接成文本，让 LLM 选一个工具名
> - 阶段二：把选中工具的完整 schema（参数名、类型、是否必填）给 LLM，填参数
>
> 为什么两阶段比一步好：21 个工具 × 平均 3 个参数 = 63 维搜索空间，LLM 一次做完准确率只有 60%。拆成 21 维（选工具）+ 3 维（填参数）后准确率提到 95%+。
>
> 参数拿回来不是直接用的——用 `inspect.signature` 做确定性校验：多余参数丢弃、缺失必填参数退回重问。prompt 约束是 99%，代码校验是 100%。

**5. 安全检测**

> 银行场景安全是第一位。做了两层：DFA 敏感词检测器——用 Trie 树存了 2 万多条危险命令和敏感词，O(n) 时间复杂度；微调 XLNet 模型做隐式风险分类——比如 "帮我把生产库的数据全删了重建" 这种不含敏感词但明显危险的话，XLNet 能在 500ms 内判定为高风险。输入和输出两端都过安全检测。

### 2.4 面试官常追问的问题

**Q：为什么不用 LangChain？**

> 评估过的。LangChain 现在有 EnsembleRetriever + RRF 可以做混合检索——但它是把两个独立的 Retriever 结果拼起来排序，管不了数据存哪。我们场景的核心需求是 openGauss 一张表同时搞定向量和 BM25，不用跨系统——LangChain 没有 openGauss 的原生 retriever，要写的话和自研 BaseRetriever 工作量差不多。第二个原因是 LangChain 的 AgentExecutor 是 ReAct 循环，LLM 自由探索工具路径——在数据库诊断场景很危险，可能跳过关键排查步骤。我们改成了诊断树引导的确定性路径。第三是 openGauss 的 GSDiskANN 索引和 `<->` L2 操作符 LangChain 没有集成——一旦用了这些原生能力，LangChain 的抽象层反而变成负担。
>
> 我们用 LangChain 的 `RecursiveCharacterTextSplitter` 做过快速原型验证，证明分块思路是对的。但核心链路——检索管道、Agent 执行循环、工具注册系统、提示模板管理——全部自研。

**Q：向量数据库为什么用 openGauss 而不是 Milvus？**

> 三个原因。一是 openGauss 一张表同时支持 floatvector + BM25，混合检索不需要跨系统。二是 GSDiskANN 是磁盘索引，百万级数据量不用全内存——银行场景文档量大，全内存成本高。三是银行已经部署了 openGauss，不需要额外引进新组件，运维团队也会维护。

**Q：两阶段工具调用准确率 95% 怎么算出来的？**

> 在银行的 1614 个真实问题上统计的。这 1614 个问题涵盖了 34 个运维场景，每个问题人工标注了正确答案（该调哪个工具、什么参数）。跑一轮工具调用，和标注对比——阶段一选对工具的比例是 95%+，阶段二填对参数的比例是 99%+。一步到位（不拆分）时只有 60%。

**Q：HyDE 降级是什么意思？为什么能提升召回率？**

> 假设文档嵌入。用户问题可能很短、术语不规范——比如 "备机重建失败怎么办"。LLM 生成一个假设答案："备机重建失败可能是因为网络中断、WAL 日志不连续、或者 gs_ctl build 命令参数错误……" 这个假设答案更长、术语更规范，用它做向量检索比用原始问题效果好。本质是用 LLM 的生成能力弥补检索的匹配能力。

**Q：如果把这个项目做更大，下一步是什么？**

> 三个方向。一是多 Agent 协同诊断——现在已经在设计诊断树驱动的多 Agent 交叉审查，提高复杂场景的根因定位准确率。二是主动巡检——定时扫描集群健康状态，不等用户问就发现问题。三是多云适配——现在适配了 openGauss，下一步可以扩展到其他数据库。

- ✅ "我们选了 openGauss 做向量数据库，因为一张表同时支持向量和 BM25"
- ✅ "两阶段方案让 6 种模型都能用同一套流程，不绑特定 API"

- ❌ "Demo 里用的 Chroma，原项目用 openGauss"

- ❌ "安全方面我只用了距离阈值，原项目有 DFA"

**项目就是 GaussMaster。你做的每一行代码都是 GaussMaster 的一部分。讲的时候用 "我们" 或用具体决策的口吻。**
