# 分块算法实际运行流程图解

## 核心算法

`RecursiveCharacterTextSplitter` 不是"一刀切到 500 字"——它是**先尝试保持结构，拆不动才降级**。

```
separators = ["\n## ", "\n### ", "\n", " ", ""]
              ↑标题      ↑子标题    ↑段落  ↑词  ↑字符（兜底）
              优先级最高 ──────────────────→ 优先级最低
```

                   └──────────────┬──────────────────┘

## 二、具体案例

以 `data/cpu_tuning.md` 为例，50 行 / 1673 字：

```
# CPU 使用率过高诊断指南

## 问题现象                        ← ① "\n## " 切在这里
当 GaussDB CPU 超过 80%...（~35字）

## 常见原因                        ← ① "\n## " 切在这里
### 1. 慢 SQL 导致 CPU 飙升        ← ③ 内部有 "\n### "，但章节段 <= 500，不触发②
大量慢 SQL...（~100字含代码块）
### 2. 统计信息过期
统计信息过期...（~50字）
### 3. 连接数过多
当连接数超过...（~120字）
### 4. 参数配置不当
检查以下参数...（~80字）
                                    ↑ 这整个"常见原因"段约 400 字

## 排查步骤                        ← ① "\n## " 切在这里
1. 执行 SELECT * FROM ...（~50字）
2. 使用 EXPLAIN ANALYZE...（~50字）
3. 检查 pg_stat_user_tables...（~50字）
4. 查看 pg_stat_database...（~50字）
5. 对比参数配置...（~30字）
                                    ↑ "排查步骤"段约 250 字

## 解决方案                        ← ① "\n## " 切在这里
- 终止慢 SQL（~30字）
- 重建索引（~20字）
- 调整参数（~20字）
- 增加 CPU（~10字）
                                    ↑ "解决方案"段约 80 字
```

### 实际分块过程

```
原文按 "\n## " 切 → 得到 4 个段：

段A: "# CPU 使用率过高诊断指南\n\n"                     (20字)
段B: "## 问题现象\n当 GaussDB CPU 超过 80%..."          (55字)
段C: "## 常见原因\n\n### 1. 慢 SQL...\n### 2. 统计信息...\n### 3. 连接数...\n### 4. 参数..."  (400字)
段D: "## 排查步骤\n1. ...\n2. ...\n3. ...\n4. ...\n5. ..."  (250字)
段E: "## 解决方案\n- 终止...\n- 重建...\n- 调整...\n- 增加..."  (80字)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
合并阶段（相邻段拼一起，尽量接近 500 字）：
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

当前块 = 段A (20字)                         20 < 500 ✅ 继续
当前块 = 段A+段B (20+55=75字)               75 < 500 ✅ 继续
当前块 = 段A+段B+段C (75+400=475字)        475 < 500 ✅ 继续
当前块 = 段A+段B+段C+段D (475+250=725字)    725 > 500 ❌ 
  → 提交块1 = [段A + 段B + 段C] ✅  (475字)
  → 新块   = [段D]                       (250字, 从段D开始)
当前块 = 段D+段E (250+80=330字)            330 < 500 ✅ 继续
  → 用完所有段，提交块2 = [段D + 段E] ✅  (330字)

最终: 2 个块

块1 (475字): "# CPU 使用率过高诊断指南\n\n## 问题现象：...\n## 常见原因：\n### 1.慢SQL...\n### 2.统计信息...\n### 3.连接数...\n### 4.参数配置..."
块2 (330字): "## 排查步骤\n1. ...\n2. ...\n3. ...\n4. ...\n5. ...\n## 解决方案\n- 终止慢SQL\n- 重建索引\n- 调整参数\n- 增加CPU"
```

### overlap=50 的影响

```
块1 结尾（最后 50 字）:
  "...建议：检查 shared_buffers、work_mem、max_parallel_workers 参数是否合理。"

块2 开头（前 50 字，从块1 倒数第 50 字抄过来）:
  "max_parallel_workers 参数是否合理。\n\n## 排查步骤\n1. 执行..."
   └────── overlap ──────┘   └────── 新内容 ──────────────────┘
```

## 三、极端情况对比

### 情况 A：章节很短（< 500 字）

```
原文:
  ## A 小节 (30字)
  ## B 小节 (80字)  
  ## C 小节 (200字)
  ## D 小节 (350字)

过程:
  按 "\n## " 切成 4 段，每段都 < 500

  合并:
  段A+段B (30+80=110) < 500 ✅
  段A+段B+段C (110+200=310) < 500 ✅  
  段A+段B+段C+段D (310+350=660) > 500 ❌ → 提交块1=[A+B+C]
  段D (350) < 500 ✅ → 提交块2=[D]

结果: 块1 310字, 块2 350字

LLM 看到块1: "## A...+## B...+## C..."  ← 三个章节拼一块，语义完整
LLM 看到块2: "## D..."                   ← 独立章节，语义完整
```

### 情况 B：单个段落超级长（> 500 字，且没有 ## 和 ### 可以切）

```
原文:
  一个超长的纯文本段 (800字)，全文没有任何 "## " 或 "### "

过程:
  ① 按 "\n## " 切 → 没找到，整段保留
  ② 按 "\n### " 切 → 没找到，整段保留  
  ③ 按 "\n" 切   → 找到 3 个段落
       段1: 350字 ← ≤ 500 ✅ 保持
       段2: 280字 ← ≤ 500 ✅ 保持
       段3: 170字 ← ≤ 500 ✅ 保持

  合并:
  段1+段2 (350+280=630) > 500 ❌ → 块1=[段1]
  段2+段3 (280+170=450) ≤ 500 ✅ → 块2=[段2+段3]

结果: 块1 350字, 块2 450字

⚠️ 问题: 块1 开头就是段落中间，没有标题
LLM 看到: "当 CPU 使用率超过阈值时，首先需要..."  ← 不知道这是哪个章节的
```

### 情况 C：单段 800 字，连 "\n" 都没有（纯代码块）

```
原文:
  ```sql
  [800字的超长 SQL，没有任何换行符]
  ```

过程:
  ① "\n## " → 没找到
  ② "\n### " → 没找到
  ③ "\n"    → 没找到（全在代码块里，没有空行）
  ④ " "     → 按空格切成单词段，每段 ≤ 500
  ⑤ ""      → 兜底方案，强制按字符切到 500

结果: 被暴力切成 ~2 块，可能从 SQL 关键字中间断开
```

## 四、设计取舍总结

| 维度 | 做法 | 好处 | 代价 |
|------|------|------|------|
| 优先按标题切 | separators 第一优先级 `\n## ` | LLM 看到每块都有章节标题，知道上下文 | 章节如果很短会多拼几个，块内主题可能跳跃 |
| overlap=50 | 相邻块重叠尾部 50 字 | 关键词不会正好断在边界上 | 块 2 开头可能从半句话开始，缺标题 |
| 降级策略 | `## `→`### `→`\n`→` `→字符 | 保证任何文档都能切，不会出错 | 越往后越粗暴，到 `\n` 以下就丢了结构 |

**总体评价**：数据库产品文档的典型结构是 "短标题 + 短段落"，和标题驱动分块高度匹配。只有遇到超大纯文本段或大代码块时才降级——而降级本身是可接受的，因为这类内容本来就不适合做向量检索的独立块。
