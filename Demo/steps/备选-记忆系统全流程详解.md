# GaussMaster 记忆系统全流程详解

> 面向面试，完整拆解 RAG 路径和 Agent 路径各自独立的记忆体系。

---

## 一、开场：记忆系统在干什么

> ① 系统需要在多轮对话中记住上下文——用户前一轮问了 CPU，后一轮说 "那慢 SQL 呢"，系统必须知道 "那" 指的是什么。② 如果每轮都失忆，Agent 会反复让 LLM 重新选工具——明明上一轮已经选了 `get_cpu_usage` 只是缺参数，下一轮用户补了参数，LLM 却要从 21 个工具里重新猜。③ Agent 路径我做了三层记忆：SESSION_TOOL_HISTORY 记当前工具名（纯内存，一个字符串），SESSION_QA_HISTORY 记对话上下文（纯内存，明文，3 轮滑动窗口），tb_interaction_memory 做持久化（MetaDatabase，AES-256 加密）。RAG 路径单独用 qa_record 表。④ 为什么分三层——工具状态只需一个值，对话上下文需多条记录，持久化需加密。三样东西生命周期和读写模式完全不同，拆开比揉在一起清晰。⑤ 3 轮滑动窗口自动淘汰，服务重启从 MetaDatabase 恢复，热数据走内存零延迟。

---

## 二、两套记忆完全独立，互不交叉

| | RAG 路径 | Agent 路径 |
|---|---|---|
| 持久化表 | `qa_record` | `tb_interaction_memory` |
| 所在库 | vector_dbname | metadatabase |
| 连接方式 | psycopg2 直连 | SQLAlchemy ORM |
| 加密 | 不加密 | AES-256-CBC（question / answer / llm_name / function_call） |
| 内存缓存 | 无 | SESSION_QA_HISTORY（明文 dict） |
| 工具状态缓存 | 不涉及 | SESSION_TOOL_HISTORY（工具名字符串） |

**同一个用户同一个会话**，RAG 问答记到 `qa_record`，Agent 工具调用记到 `tb_interaction_memory`——代码层面互不读写对方的表。

## 三、Agent 路径：三层记忆 + 读写全链路

### 3.1 SESSION_TOOL_HISTORY —— 当前正在调哪个工具

```python
SESSION_TOOL_HISTORY = {}  # {user_id: {session_id: "risk_analysis"}}
```

| 属性 | 值 |
|------|-----|
| 存什么 | 一个字符串——当前正在交互的工具名 |
| 生命周期 | 工具调用结束后立即清空 |
| 持久化 | **❌ 没有持久化，纯进程内存，重启丢失** |
| 目的 | 避免 LLM 重复选工具，省一次 API 调用 |

**为什么它不需要持久化**：就算重启丢了，无非是下一轮 LLM 重新选一次工具——多花一次 API 调用而已，不影响正确性。

---

### 3.2 SESSION_QA_HISTORY —— 对话上下文缓存

```python
SESSION_QA_HISTORY = {}  # {user_id: {session_id: [InteractionMemory, ...]}}
```

| 属性 | 值 |
|------|-----|
| 存什么 | 最近 3 轮的完整对话记录（InteractionMemory 对象列表） |
| 持久化 | **❌ 没有持久化，纯进程内存，重启丢失** |
| 为什么不怕丢 | 丢了从 tb_interaction_memory 查回来 |

**它不是持久化层，是持久化层的影子缓存**——提速用的。相当于 Redis 缓存，挂了从 MySQL 补。

---

### 3.3 tb_interaction_memory —— 真正的持久化层

```
所在库: metadatabase (SQLAlchemy ORM 连接)
```

| 字段 | 是否加密 | 示例值 |
|------|---------|--------|
| qa_record_id | 否 | `"a3f2b1c4d5e6..."` |
| user_id | 否 | `"zhangsan"` |
| session_id | 否 | `"sess_001"` |
| **question** | **AES-256** | `"帮我查一下 db_001 的 CPU 使用率"` |
| **answer** | **AES-256** | `"CPU 使用率 78.5%，建议排查慢 SQL"` |
| **llm_name** | **AES-256** | `"pangu_sigma_38b"` |
| **function_call** | **AES-256** | `'{"name":"get_cpu_usage","arguments":{"instance":"db_001"}}'` |
| created_at | 否 | `1718294400000` |

**为什么 user_id / session_id 不加密**：这是查询条件——`WHERE user_id=? AND session_id=?`——加密了就查不到了。

**为什么 question / answer / function_call 加密**：银行场景，对话内容可能含实例名、IP、SQL 片段、调了什么工具什么参数。内存里是明文（快），落库变成密文（安全）。

---

### 3.4 读的完整链路

```python
async def get_qa_history(self):                           # dba.py:197
    # ─── 第一优先：翻进程内存 ───
    qa_list = SESSION_QA_HISTORY[user_id][session_id][:history_len]
    if qa_list:
        return qa_list  # 命中！零数据库 IO，< 1ms

    # ─── 第二优先：查 MetaDatabase ───
    raw_records = await select_interaction_memory(user_id, session_id, history_len)
    # → SELECT * FROM tb_interaction_memory
    #   WHERE user_id=? AND session_id=? ORDER BY created_at DESC LIMIT 3

    # → AES-256-CBC 逐条解密
    for r in raw_records:
        r.question = Encryption.decrypt(r.question)
        r.answer = Encryption.decrypt(r.answer)
        r.function_call = Encryption.decrypt(r.function_call)

    # → 回填进程内存，加速下次访问
    SESSION_QA_HISTORY[user_id] = {session_id: raw_records}
    return raw_records
```

| 场景 | 数据来源 | 延迟 |
|------|---------|------|
| 用户刚聊过 | SESSION_QA_HISTORY 内存 | < 1ms |
| 服务刚重启 | tb_interaction_memory → 解密 → 回填 | ~10ms |
| 第二次访问（已回填） | SESSION_QA_HISTORY 内存 | < 1ms |

### 3.5 写的完整链路

```python
async def generate_record_and_save(self, answer, function_call=None):  # dba.py:105
    qa_record = InteractionMemory(
        qa_record_id=str(uuid.uuid4().hex),
        user_id=self.user_id, session_id=self.session_id,
        question=self.question,
        answer=answer,
        llm_name=self.llm.name,
        function_call=function_call,       # None 或 JSON字符串
        created_at=int(time.time() * 1000)
    )

    # ① 写进程内存 —— 明文，3 轮滑动窗口
    add_to_local_memory(SESSION_QA_HISTORY, self.history_len, qa_record)

    # ② 写 MetaDatabase —— AES-256 密文，持久化
    await insert_interaction_memory(
        qa_record_id=qa_record.qa_record_id,
        user_id=qa_record.user_id,
        session_id=qa_record.session_id,
        question=Encryption.encrypt(qa_record.question),
        answer=Encryption.encrypt(qa_record.answer),
        llm_name=Encryption.encrypt(qa_record.llm_name),
        function_call=Encryption.encrypt(qa_record.function_call) if qa_record.function_call else None,
        created_at=qa_record.created_at
    )
```

**两条路同时走**——不是二选一。内存快但不持久，数据库持久但慢。同时写两处，读的时候内存优先。

### 3.6 滑动窗口淘汰

```python
def add_to_local_memory(local_qa, length, qa):
    qa_list = local_qa[qa.user_id].get(qa.session_id, [])
    qa_list.append(qa)
    while len(qa_list) > length:     # 超过 3 轮？
        qa_list.pop(0)               # 扔最旧的
```

```
第1轮: [Q1, A1]
第2轮: [Q1, A1, Q2, A2]
第3轮: [Q1, A1, Q2, A2, Q3, A3]
第4轮: [Q2, A2, Q3, A3, Q4, A4]  ← Q1 被淘汰，内存和数据库都只存最新 3 条
```

### 3.7 历史怎么注入 LLM prompt

```python
# 拼进消息列表前，把 function_call 也带上
history = []
for qa in qa_record_history:
    history.append({"role": "user", "content": qa.question})
    answer_dict = {"role": "assistant", "content": qa.answer}
    if qa.function_call:
        answer_dict["function"] = qa.function_call  # 盘古拿到这个知道 "上次调了什么工具"
    history.append(answer_dict)

message_inputs = history + [{"role": "user", "content": current_question}]
```

LLM 看到上一轮 Assistant 返回里有 `function_call: {"name": "risk_analysis"}`，就知道 "系统刚才查了 CPU 指标"——下一轮说 "继续预测" 时能接上。

## 四、RAG 路径：qa_record 表

```
所在库: vector_dbname (openGauss, psycopg2 直连)
不加密，不走内存缓存
```

| 字段 | 说明 |
|------|------|
| user_id / session_id | 用户和会话 |
| question / answer | 问题和答案（**明文**——RAG 内容都是公开文档知识） |
| vector_topk / text_topk / rerank_topk | 检索参数 |
| model_name | 用的哪个 LLM |
| like / hate / feedback_info | 用户反馈 |
| create_time | 时间 |

**为什么 RAG 不加密**：RAG 问答内容都是公开的产品文档——"CPU 过高怎么排查"、"shared_buffers 建议值多少"。没有敏感信息。

**为什么 RAG 没有内存缓存**：RAG 读历史频率低——每次请求只读一次，查表 10ms 完全可接受。Agent 高频读写才需要内存加速。

```python
# 读: ask_gauss() 开头
history = get_history_chat(user_id, session_id, history_len)
  → SELECT * FROM qa_record WHERE user_id=... ORDER BY create_time DESC LIMIT 3

# 写: ask_gauss() 结束（finally 块保证一定写）
insert_qa_record(qa_dict)
```

## 五、面试 5 步法完整版

> ① 系统需要记住多轮对话上下文——用户补参数时要知道 "上次选的什么工具"，追问时要知道 "刚才聊了什么"。② 如果不记状态，每一轮都是全新的，LLM 要从 21 个工具里重新猜——用户说 "48 小时"，LLM 不知道这是补充参数还是新问题。③ Agent 路径三层：SESSION_TOOL_HISTORY 记当前工具名（纯内存字符串），SESSION_QA_HISTORY 记对话上下文（纯内存 dict），tb_interaction_memory 做真正的持久化（AES-256 加密写 MetaDatabase）。读写全链路：写的时候内存 + 数据库双写，读的时候先翻内存，没有才查数据库解密回填。RAG 路径单独用 qa_record 表——内容都是公开知识，不加密也没有内存缓存。④ 为什么分三层——工具状态只需一个值不需要持久化，对话上下文多轮需要持久化但内存优先更快，持久化层必须加密因为可能含实例名和 SQL 片段。三样东西各管各的，拆开比揉在一起清晰。⑤ 3 轮滑动窗口自动淘汰，服务重启从 MetaDatabase 恢复，热数据走内存零延迟。
