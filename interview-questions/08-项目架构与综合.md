# 项目架构与综合面试题

## 一、架构设计

### Q1: 请整体介绍一下 GaussMaster 的架构。

**回答要点**：
```
┌─────────────────────────────────────────┐
│              前端 (Web UI)               │
└─────────────────────────────────────────┘
                    │ HTTP / SSE
┌─────────────────────────────────────────┐
│           API 层 (FastAPI)               │
│  ├─ controllers/core.py                  │
│  ├─ 参数校验 (ParameterChecker)          │
│  └─ 响应标准化 (standardized_xxx)        │
└─────────────────────────────────────────┘
                    │
┌─────────────────────────────────────────┐
│         业务层 (data_transformer)         │
│  ├─ 检索 (search)                        │
│  ├─ 推理 (infer/ask_gauss)               │
│  ├─ 查询优化 (query_opt_process)          │
│  └─ 知识库管理 (add_knowledge)            │
└─────────────────────────────────────────┘
                    │
┌─────────────────────────────────────────┐
│         Agent 层 (multiagents)            │
│  ├─ Planner (意图识别)                   │
│  ├─ DBA Agent (工具调用)                 │

└─────────────────────────────────────────┘
                    │
┌─────────────────────────────────────────┐
│         基础设施层 (common)               │
│  ├─ HTTP 通信 (http/)                    │
```

**核心设计原则**：
- 分层架构，每层职责单一
- 装饰器模式解耦框架和业务
- 异步编程提升 IO 性能

### Q2: 为什么选择 RAG 而不是直接微调模型？

**回答要点**：
| 方案 | 优点 | 缺点 |
|:---|:---|:---|
| RAG | 知识更新快（改数据库即可）、可解释性强（有引用来源）、成本低 | 依赖检索质量 |
| 微调 | 知识内化到模型、不依赖外部检索 | 训练成本高、知识更新需重新训练、幻觉风险 |

**选择 RAG 的原因**：
- 数据库知识频繁更新（版本迭代、新案例），RAG 更灵活
- 需要给出知识来源，增强可信度
- 运维场景对准确性要求高，RAG 的检索结果可验证

---

### Q3: 系统的扩展性怎么保证？

**回答要点**：
1. **水平扩展**：FastAPI 是无状态的，可以部署多实例，前面加负载均衡
2. **模型切换**：支持多个 LLM 在线切换，某个模型不可用自动降级
3. **知识库扩展**：支持自定义知识库，动态创建向量表
4. **工具扩展**：Registry 模式，新工具只需加装饰器
5. **插件机制**：预留了插件接口，支持第三方扩展

---

## 二、性能优化

### Q4: 系统的性能瓶颈可能在哪里？怎么优化？

**回答要点**：
| 瓶颈 | 原因 | 优化方案 |
|:---|:---|:---|
| LLM 调用 | 生成耗时 | 流式输出、缓存热门回答、模型蒸馏 |
| 向量检索 | ANN 计算 | 优化索引、降维、分片 |
| 数据库查询 | IO 延迟 | 连接池、缓存、读写分离 |
| 网络传输 | SSL/TLS 握手 | 连接复用、Session 缓存 |

---

### Q5: 流式输出对用户体验有什么提升？有什么代价？

**回答要点**：
**提升**：
- 降低首字延迟，用户感知速度更快
- 实时看到生成过程，减少焦虑感
- 可以中途停止，节省资源

**代价**：
- 服务端复杂度增加（异步生成器、SSE 协议）
- 前端需要处理流式渲染
- 网络不稳定时可能断流

---

## 三、异常处理

### Q6: 系统的异常处理策略是什么？

**回答要点**：
1. **分层捕获**：
   - Controller 层：`standardized_api_output` 统一包装
   - Service 层：业务异常抛出自定义异常
   - DAO 层：数据库异常转换为用户友好消息

2. **流式异常**：
   - `standardized_event_stream_output` 捕获异常
   - yield 错误消息，避免流中断

3. **降级策略**：
   - LLM 不可用 → 切换到备用模型
   - 检索为空 → 返回拒答，不瞎编
   - DBMind 不可用 → 返回友好提示

---

### Q7: 如果 LLM 服务完全不可用，系统还能提供什么能力？

**回答要点**：
- **检索能力**：用户可以直接搜索知识库，看原始文档
- **工具能力**：部分工具不依赖 LLM，可以直接调用 DBMind
- **历史查看**：查看之前的问答记录
- **完全不可用时的提示**："LLM 服务暂时不可用，请稍后重试"

## 六、综合手写题

### 题目：设计一个高可用的 LLM 调用网关

```python
import asyncio
import random
from enum import Enum

class CircuitState(Enum):
    CLOSED = "closed"      # 正常
    OPEN = "open"          # 熔断
    HALF_OPEN = "half_open" # 半开

class LLMGateway:
    def __init__(self, providers):
        self.providers = providers  # List[LLMProvider]
        self.circuit_states = {p.name: CircuitState.CLOSED for p in providers}
        self.failure_counts = {p.name: 0 for p in providers}
        self.success_counts = {p.name: 0 for p in providers}
        self.threshold = 5  # 熔断阈值
    
    async def call(self, messages, timeout=30):
        # 选择可用的 provider
        available = [
            p for p in self.providers
            if self.circuit_states[p.name] != CircuitState.OPEN
        ]
        
        if not available:
            raise Exception("All LLM providers unavailable")
        
        # 随机选择（可以改为轮询或权重）
        provider = random.choice(available)
        
        try:
            result = await asyncio.wait_for(
                provider.generate(messages),
                timeout=timeout
            )
            # 成功，重置失败计数
            self.failure_counts[provider.name] = 0
            self.success_counts[provider.name] += 1
            
            if self.circuit_states[provider.name] == CircuitState.HALF_OPEN:
                self.circuit_states[provider.name] = CircuitState.CLOSED
            
            return result
            
        except Exception as e:
            # 失败，增加计数
            self.failure_counts[provider.name] += 1
            
            if self.failure_counts[provider.name] >= self.threshold:
                self.circuit_states[provider.name] = CircuitState.OPEN
                # 异步恢复
                asyncio.create_task(self._try_recover(provider))
            
            # 重试其他 provider
            remaining = [p for p in available if p != provider]
            if remaining:
                return await self.call(messages, timeout)
            raise
    
    async def _try_recover(self, provider):
        await asyncio.sleep(30)  # 30秒后尝试恢复
        self.circuit_states[provider.name] = CircuitState.HALF_OPEN


class LLMProvider:
    def __init__(self, name, url):
        self.name = name
        self.url = url
    
    async def generate(self, messages):
        # 实际调用 LLM
        pass
```
