# 记忆机制面试题

## 一、基础问题

### Q1: 系统的记忆机制分几层？每层的作用是什么？

**回答要点**：
| 层级 | 名称 | 存储介质 | 作用范围 | 用途 |
|:---|:---|:---|:---|:---|
| 第一层 | 进程级本地缓存 | Python dict | 进程生命周期 | 加速读取，供 LLM 上下文使用 |
| 第二层 | 关系型元数据库 | openGauss | 持久化 | 长期保存，跨会话/重启恢复 |
| 第三层 | 向量数据库 | openGauss + 向量索引 | 持久化 | 语义检索，找历史相似问题 |

---

### Q2: 本地内存缓存的结构是怎样的？怎么保证线程安全？

**回答要点**：
```python
# global_vars.py
SESSION_QA_HISTORY = {}                 # {user_id: {session_id: [InteractionMemory, ...]}}
SESSION_TOOL_HISTORY = defaultdict(dict) # {user_id: {session_id: "tool_name"}}
```
- 按 `user_id + session_id` 两级隔离，避免数据串扰
- Python 的 GIL 保证 dict 操作原子性，不需要额外锁
- 容量限制：`history_len` 控制，超出时 FIFO（`pop(0)`）

---

### Q3: 关系型数据库里存了哪些字段？为什么加密？

**回答要点**：
表 `tb_interaction_memory`：
| 字段 | 说明 |
|:---|:---|
| `qa_record_id` | 主键 |
| `user_id` / `session_id` | 归属标识 |
| `question` | 用户问题（**加密**） |
| `answer` | 助手回答（**加密**） |
| `function_call` | 工具调用信息（**加密**） |
| `llm_name` | 使用的模型 |
| `created_at` | 时间戳 |

**加密原因**：
- 对话内容可能包含敏感信息（数据库密码、业务数据等）
- 使用 `Encryption.encrypt()` / `Encryption.decrypt()` 对称加密
- 即使数据库被拖库，攻击者也无法直接读取内容

## 二、进阶问题

### Q4: 三层记忆的协作流程是怎样的？

**回答要点**：
```
用户提问
    │
    ▼
1. 读取历史（get_qa_history）
    ├── 先查本地缓存 SESSION_QA_HISTORY
    ├── 缓存未命中 → 查元数据库 tb_interaction_memory
    └── 查到后回填内存（加速下次访问）
    │
    ▼
2. LLM 推理（携带历史上下文）
    │
    ▼
3. 保存记录（generate_record_and_save）
    ├── 写入本地缓存 SESSION_QA_HISTORY
    ├── 异步写入元数据库（加密存储）
    └── 可选：写入向量库（语义检索）
```

---

### Q5: 什么时候写入本地内存？什么时候写入数据库？

**回答要点**：
| 操作 | 时机 | 方式 |
|:---|:---|:---|
| 写本地内存 | 每次对话结束后立即 | 同步 |
| 写关系型数据库 | 每次对话结束后 | 异步（`await insert_interaction_memory`） |
| 写向量库 | 当前代码中主要是预留 | 未实时写入 |

**双写策略**：
- 本地内存和数据库**同时写入**
- 数据库是异步非阻塞的，不影响响应速度
- `finally` 块确保即使异常也要落库

---

### Q6: `history_len` 参数怎么控制？为什么默认是 1-3？

**回答要点**：
- `history_len` 限制加载的历史轮数，范围 `[0, 3]`
- 原因：
  1. **上下文长度限制**：LLM 有 Token 上限，历史太长会挤占当前问题的空间
  2. **相关性衰减**：太久远的对话对当前问题帮助不大
  3. **成本考虑**：历史越长，API 调用费用越高
  4. **速度考虑**：历史长 → Prompt 长 → 生成慢

---

### Q7: 工具意图记忆（SESSION_TOOL_HISTORY）是什么？

**回答要点**：
- 记录当前会话**未完成的工具意图**
- 示例：
  - 用户说"帮我查一下慢 SQL"，但没给时间参数
  - 系统记录意图是 `slow_sql_rca`
  - 下轮对话继续追问参数，而不是重新理解意图
- 本质是一个**状态机记忆**，不是历史记录

---

## 三、深挖问题

### Q8: 如果服务重启，本地缓存丢了，怎么恢复？

**回答要点**：
1. 重启后首次对话，本地缓存为空
2. `get_qa_history()` 自动从元数据库查询最近 N 条
3. 查询结果**回填到本地缓存**（`SESSION_QA_HISTORY`）
4. 后续对话直接从内存读取，加速访问

**优化点**：
- 可以考虑启动时预热缓存，批量加载活跃用户的历史

---

### Q9: 向量库 `gm_tool_history_memory` 目前怎么用？

**回答要点**：
- 表结构：
  - `question`：问题原文
  - `question_vector`：1024 维 floatvector
  - `tool_name`：调用的工具名
  - `user_id` / `user_name` / `created_at`
- 当前状态：
  - 表已定义，初始化时建表
  - **实时写入逻辑在核心流程中未直接调用**
  - 可能是预留功能，用于后续"相似问题推荐"

---

### Q10: 如果让你优化记忆机制，你会怎么做？

**回答要点**：
1. **缓存预热**：启动时批量加载活跃用户历史，减少首次查询延迟
2. **缓存淘汰策略**：当前是 FIFO，可以改为 LRU（最近最少使用）
3. **向量库启用**：实现实时写入，支持"以前有没有类似问题"的语义检索
4. **记忆摘要**：历史太长时，用 LLM 生成摘要，替代原始对话
5. **跨会话记忆**：当前记忆按 session 隔离，可以支持用户级长期记忆

## 四、手写代码题

### 题目：实现一个带容量限制的 LRU 记忆缓存

```python
from collections import OrderedDict

class LRUMemoryCache:
    def __init__(self, capacity=100):
        self.capacity = capacity
        self.cache = OrderedDict()
    
    def get(self, user_id, session_id):
        key = (user_id, session_id)
        if key not in self.cache:
            return None
        # 移到末尾（最近使用）
        self.cache.move_to_end(key)
        return self.cache[key]
    
    def put(self, user_id, session_id, qa_list):
        key = (user_id, session_id)
        self.cache[key] = qa_list
        self.cache.move_to_end(key)
        
        # 超出容量，淘汰最旧的
        while len(self.cache) > self.capacity:
            self.cache.popitem(last=False)
    
    def add_qa(self, user_id, session_id, qa):
        key = (user_id, session_id)
        if key not in self.cache:
            self.cache[key] = []
        self.cache[key].append(qa)
        
        # 限制单用户历史长度
        while len(self.cache[key]) > 3:
            self.cache[key].pop(0)
        
        self.cache.move_to_end(key)
```
