# GaussMaster：基于 LLM 的数据库智能运维 Copilot

## 项目概述

GaussMaster 是华为 openGauss 开源社区的一个 AI 原生数据库运维系统。核心思路是：**用大语言模型充当 DBA 的 Copilot**，让运维人员通过自然语言就能完成数据库的问答、故障诊断、性能调优等全生命周期工作。

这个项目已在**中国农业银行生产环境落地**，覆盖 34 个运维场景实现零人工干预，QA 回答高质量率 85%+，工具调用准确率 95%+。2025 年 6 月相关论文发表在 arXiv 上。

---

## 一、为什么做这个项目

### 传统数据库运维的三大痛点

**痛点一：知识壁垒高。** 一个 GaussDB DBA 需要熟读上千页的产品手册、排障文档、接口文档。遇到一个告警，可能要先翻半小时文档才能确定排查方向。银行新来的 DBA 上手周期长达 3-6 个月。

**痛点二：自动化工具各自为战。** 业内有 NL2SQL、异常检测、慢 SQL 优化这些单点工具，但它们彼此独立，无法串联。比如 CPU 飙高告警来了，你需要分别去查指标平台、慢查询平台、锁分析平台，然后人脑整合——中间任何一步出错都可能导致误判。

**痛点三：通用大模型用不了。** 直接拿 ChatGPT/DeepSeek 问 GaussDB 问题会出大事——它不了解 GaussDB 专有语法，会把 PostgreSQL 的经验套过来，甚至给出"DROP TABLE"这种危险建议。我们实测了 1614 个真实银行问题，通用模型要么答不上来，要么直接给错误答案。

### 所以我们要做的是

一个能用自然语言对话的数据库专家系统。它有四个核心能力：

1. **智能问答**：问什么答什么，答案来自真实文档，不是模型编的
2. **故障诊断**：告警来了自动分析根因，给出修复建议
3. **主动巡检**：定期检查集群健康状态
4. **预测调优**：提前发现风险，给出优化方案

## 二、系统架构

整体分为三大部分：**知识层**、**推理层**、**执行层**。

```
┌─────────────────────────────────────────────────────┐
│  用户： "为什么 CPU 突然飙到 90%？"                   │
└──────────────────────┬──────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────┐
│  推理层：GaussMaster 主服务                           │
│                                                     │
│  ┌───────────┐  ┌───────────┐  ┌────────────────┐  │
│  │ RAG 问答  │  │ Agent 诊断│  │ 多 Agent 协调  │  │
│  │ 管道      │  │ 工具编排  │  │ 交叉审查       │  │
│  └─────┬─────┘  └─────┬─────┘  └───────┬────────┘  │
│        │              │                 │            │
└────────┼──────────────┼─────────────────┼────────────┘
         │              │                 │
         ▼              ▼                 ▼
┌─────────────────────────────────────────────────────┐
│  知识层                        执行层                │
│  ┌───────────┐           ┌──────────────────┐      │
│  │ 向量数据库 │           │ DBMind 平台      │      │
│  │ +BM25 索引│           │ · 指标监控       │      │
│  │ +重排序   │           │ · 慢 SQL 分析    │      │
│  └───────────┘           │ · 锁检测         │      │
│                          │ · 参数调优       │      │
│  ┌───────────┐           │ · 告警管理       │      │
│  │ LLM 推理  │           └──────────────────┘      │
│  │ 盘古/DeepSeek│                                   │
│  └───────────┘                                      │
└─────────────────────────────────────────────────────┘
```

**知识层**负责"知道什么"——把 GaussDB 的文档、排障手册、历史案例全部向量化存储，检索时做向量 + 关键词混合搜索，再经过重排序确保相关性。

**推理层**负责"怎么想"——收到用户问题后，先判断是问答类还是诊断类。问答类走 RAG 管道，诊断类走 Agent 工具编排，复杂场景启动多 Agent 协同诊断。

**执行层**负责"动手做"——通过 DBMind 平台纳管 openGauss 实例，提供 21 个诊断工具（指标查询、慢 SQL 分析、锁检测等），Agent 决策后直接调用执行。

## 三、关键技术决策

### 决策一：不用 LangChain，核心链路全自研

这是面试中最常被追问的点。我们团队评估过 LangChain，最终决定不用。原因有三个：

**1. LangChain 的 RAG 不支持我们的混合检索。** 我们的检索管道是向量检索 + BM25 全文检索 + 重排序的三路混合。LangChain 的 `RetrievalQA` 只能做单路向量检索，要支持 BM25 需要大量魔改，得不偿失。

**2. LangChain 的 AgentExecutor 在诊断场景不够可控。** LangChain 的 ReAct 循环会让 Agent 自由探索工具调用路径，这在数据库诊断场景下很危险——它可能反复调同一个工具、跳过一个关键排查步骤。我们改用**诊断树引导的确定性路径**：每个故障类型对应一棵诊断树，树节点是具体工具，树路径是验证过的排查步骤，Agent 按路径走而不是自由探索。

**3. openGauss 的原生能力 LangChain 没法用。** openGauss 自带 GSDiskANN 向量索引和 BM25 全文索引，这是我们的核心武器。但 LangChain 根本没有 openGauss 的 vectorstore 集成，硬套 Chroma 或 Milvus 反而增加部署复杂度。

**所以我们的做法是**：借鉴 LangChain 的 Agent + Tool 架构思想（Agent 基类、工具注册模式、输出解析器），但所有核心链路——检索管道、Agent 执行循环、工具注册系统、提示模板管理——全部自研。这让我们对系统的每个环节都有完全的控制力。

### 决策二：不用 Milvus，直接用 openGauss 做向量数据库

这又是一个反直觉的选择。业内做 RAG 的标准方案是 "LangChain + Milvus/Pinecone + OpenAI Embedding"，但我们选择了完全不同的路线。

**为什么？** 因为我们的数据库本身就是 openGauss——一个 PostgreSQL 兼容的关系型数据库，支持 `floatvector` 列类型和 GSDiskANN 磁盘向量索引。一张表可以同时存结构化字段、文本、1024 维向量、BM25 倒排索引，混合检索不需要跨系统。

具体来说：

```
一张知识库表：
┌──────┬──────────┬──────────┬─────────────────────┬──────────┐
│ uuid │ title    │ text     │ text_vector(1024)   │ version  │
├──────┼──────────┼──────────┼─────────────────────┼──────────┤
│ a1   │ CPU 诊断 │ 当 CPU... │ [0.12, -0.34, ...] │ v7.0     │
│ a2   │ 内存调优 │ 内存参数...│ [0.45, 0.01, ...]  │ v7.0     │
└──────┴──────────┴──────────┴─────────────────────┴──────────┘
   向量索引: GSDiskANN (L2距离)    文本索引: BM25
```

向量检索用 `ORDER BY vector <-> query_vec LIMIT 10`，文本检索用 `ORDER BY text ### 'keyword' DESC LIMIT 10`，两个结果集合并后送重排序。

**GSDiskANN 索引的选型**：银行场景下文档块数量是百万级的，内存放不下全部向量。GSDiskANN 是 openGauss 基于微软 DiskANN 自研的磁盘向量索引，支持乘积量化（PQ）压缩，在精度损失可控的前提下把内存占用降低约 10 倍。具体参数：1024 维向量，PQ 段数 1024，16 个聚类中心，30 并行度。

### 决策三：不用原生 Function Call，用提示工程做工具调用

业内做工具调用的标准做法是 OpenAI Function Call API——把工具 schema 传给模型，模型返回 `function_call` 字段，然后执行。

但我们面临的问题是：项目要支持盘古、DeepSeek、ChatGLM、百川、Qwen 五种模型，它们各自的原生 Function Call 行为不一致。盘古有 `function_call` 字段，ChatGLM 没有，DeepSeek 有但参数格式不同。

**我们设计了一个统一的两阶段方案**，不依赖任何模型的原生 API：

**阶段一：工具选择。** 把 21 个工具的 name + description + 参数 schema 拼成 JSON，放进 system prompt。让 LLM 从 21 个候选里选一个最匹配的。

```
System: 你是一个数据库运维专家。以下是可以使用的工具列表：
[
  {"name": "risk_analysis", "description": "预测指标趋势", "params": ["metric": "str, 必填"]},
  {"name": "slow_sql_rca", "description": "慢SQL根因分析", "params": []},
  ...
]
用户: CPU 使用率突然飙高，帮我看看什么原因。
→ LLM 输出: risk_analysis
```

**阶段二：参数提取。** 拿到工具名后，再给 LLM 该工具的详细参数 schema，让它从用户问题里提取参数值。

```
System: risk_analysis 工具需要以下参数：
- metric (str, 必填): 需要预测的指标名称
- warning_hours (int, 可选): 预测小时数，默认24
用户: CPU 使用率突然飙高，帮我看看什么原因。
→ LLM 输出: {"metric": "cpu_usage", "warning_hours": 24}
```

**为什么分两步而不是一步？** 因为我们发现同时选工具和填参数太难了——21 个工具 × 平均 3 个参数 = 63 个候选字段，LLM 很容易出错。分两步后，第一步只需要关注 21 个工具名，第二步只需要关注 1 个工具的参数，准确率从 60%+ 提升到 95%+。

### 决策四：双层检索 + 降级策略

检索不能只靠向量。向量擅长语义匹配，但遇到专有名词（比如 "GUC 参数"、"gs_dump"）时效果很差，因为这些词在训练语料里出现少。

所以我们做了**混合检索**：向量检索 + BM25 关键词检索，两路结果合并。BM25 确保专有名词能精确命中，向量确保语义相近的也能找到。

但这还不够——如果两路都搜不到怎么办？用户可能问了一个文档里没有直接答案的问题。我们设计了**两步降级**：

**降级一：HyDE（假设文档嵌入）。** 让 LLM 先编一个"假设的完美答案"，用这个假答案的向量去检索。神奇的是，假答案的语义向量往往比原始问题的向量更接近真实文档。

**降级二：查询改写。** 让 LLM 把复杂问题拆成 3 个子问题，分别检索，结果汇总。

这两步降级把"搜不到"的概率降低了约 40%。

## 四、多 Agent 协同诊断（论文核心创新）

### 为什么需要多 Agent

单个 Agent 做诊断有一个致命问题：**认知盲区**。

比如 CPU 飙高的告警，资源专家 Agent 会分析指标发现 I/O 异常，但它的知识范围只到"指标异常"这一步，它不知道 I/O 异常可能是因为有一条慢 SQL 在扫全表。而慢 SQL 是组件专家 Agent 的领域——但没有人告诉资源专家去调用组件专家。

### 我们的方案：层次化多 Agent + 交叉审查

```
               ┌──────────────┐
               │  DBA 主 Agent │  ← 协调者，分配任务，汇总结果
               └──────┬───────┘
          ┌───────────┼───────────┐
          ▼           ▼           ▼
   ┌──────────┐ ┌──────────┐ ┌──────────┐
   │ 资源专家 │ │ 组件专家 │ │ 修复专家 │
   │ 指标分析 │ │ 慢SQL诊断│ │ 方案生成 │
   └──────────┘ └──────────┘ └──────────┘
          │           │           │
          └───────────┼───────────┘
                      ▼
              交叉审查 + 信息交换
```

**交叉审查机制**：Agent 在诊断过程中可以互相交换信息。比如资源专家发现 I/O 异常后，可以发消息给 DBA 主 Agent："我怀疑是某条慢 SQL 导致的，建议启动组件专家分析。"DBA 主 Agent 收到建议后，如果发现组件专家的结论与资源专家的假设矛盾，会让双方交叉验证。

**这解决了一个什么问题？** 单个 Agent 只能在自己的认知范围内做推理，交叉审查让不同领域的 Agent 相互补充盲区。银行实测数据显示，多 Agent 协同比单 Agent 的根因定位准确率提升了约 15%。

## 六、面试可能会追的细节

**Q: 你在这个项目里具体负责什么？**
> 核心负责 RAG 检索管道和 Agent 工具链路的设计实现。具体包括：向量 + BM25 混合检索、重排序降级策略、工具注册系统的架构设计、多模型适配的统一抽象层、以及诊断树引导的 Agent 执行循环。同时参与了银行 POC 环境的部署调优。

**Q: 遇到的最大技术挑战是什么？**
> 多模型 Function Call 的统一适配。盘古有原生 function_call 支持，DeepSeek 有但格式不同，ChatGLM 和百川完全没有。最开始我们想给每个模型单独写适配逻辑，但代码膨胀严重且难以维护。后来我们设计了统一的两阶段提示工程方案，不依赖任何模型的特殊能力，准确率反而比原生方案更高，而且所有模型都能用同一套代码。

**Q: 为什么不直接用 Dify / Coze 这类 LLMOps 平台？**
> 两个原因。一是安全合规——银行场景要求数据不出内网，文档和用户问题都不能经过公有云。二是深度定制需求——Dify 的 RAG 管道和 Agent 编排太通用，没法支持我们的 GSDiskANN 索引和诊断树引导的多 Agent 协调，最终还是要从底层改。

**Q: 如果让你重新设计，会做什么不同？**
> 一是 LLM 调用层会引入更完善的 fallback 机制——现在如果主模型挂了，切换备用模型需要手动改配置。二是会把诊断树和 Agent 解耦得更彻底，让诊断树可以作为一个独立的知识表示层，Agent 只是执行器之一。
