## 一、项目概况（开场必问）

### ★1. 介绍一下 GaussMaster 这个项目

**考察意图**：你是不是挂名打杂，还是真做了核心模块。

**得分点**：不要背 README，要说你**为什么做、负责什么、难点在哪**。

> GaussMaster 是 openGauss 社区的 AI 项目，用 LLM 做数据库智能运维。我参与是因为在内核开发时发现一个痛点——DBA 遇到告警要在多个平台来回切。我在项目里负责两个核心模块：RAG 检索管道和 Agent 工具链路。项目现在已在银行生产环境跑了，34 个场景零人工干预。

---

### ★2. 你在项目里具体负责什么？

**考察意图**：确认你的角色是核心还是边缘。

> 负责 RAG 检索管道和 Agent 工具链路。RAG 这边，评估 LangChain 后决定核心链路自研，设计了向量+BM25+重排序的三路混合检索。Agent 这边，21 个工具的接口定义、参数 schema、多模型统一适配是我主导的。

---

### 3. 项目做了多久？团队几个人？

> 从 2024 年 6 月到 2025 年 6 月，大约一年。前期调研和工具接口设计阶段投入约 30%，后期核心开发阶段全力投入。因为两个项目都在 openGauss 生态内，很多技术积累是复用的。

---

### 4. 最大的技术挑战是什么？

> 六种大模型的 Function Call 统一适配。盘古有原生 function_call、DeepSeek 有但格式不同、ChatGLM 完全没有。最初给每个模型写独立适配逻辑，代码膨胀严重且准确率参差不齐。后来设计了模型无关的两阶段方案——先选工具名、再填参数——统一了所有模型的调用接口，准确率从 60% 提升到 95%+。

## 二、RAG 检索管道（深度追问区）

### ★5. 为什么不用 LangChain？

**考察意图**：你有技术判断力还是盲目排斥框架。

> 三个原因。第一，LangChain 的 RetrievalQA 只支持单路向量检索，我们需要向量+BM25+重排序的三路混合。第二，openGauss 的 GSDiskANN 和 BM25 是原生能力，LangChain 没有对应 vectorstore 集成。第三，Agent 部分，LangChain 的 ReAct 循环太自由了，数据库诊断需要确定性路径。

---

### ★6. 检索管道具体怎么做的？

**考察意图**：你是不是只调了个 API。

> 四阶段：安全检测 → 混合检索 → 重排序 → LLM 生成。
>
> 混合检索是向量 + BM25 双路并行。向量用 BGE-large 在 10 万条 GaussDB 语料上微调，1024 维。BM25 解决专有名词的问题——"gs_dump"、"GUC 参数"这些词向量匹配效果差，但 BM25 可以精确命中。
>
> 两路结果合并后送重排序，关键设计是过滤 score<0 的结果——负相关文档进 prompt 只会带来幻觉。

---

### 7. 搜不到怎么办？（HyDE 和查询改写）

> 两层降级。第一层 HyDE——让 LLM 先生成一个假设答案，用假答案的向量去检索。因为假答案的语义向量比原始问题的向量更接近真实文档。还不行就走查询改写，让 LLM 拆成 3 个子问题分别搜。这两步把空结果概率降了约 40%。

---

### ★8. 为什么向量数据库不用 Milvus？

**考察意图**：你是不是只会 openGauss 还是真做了技术选型。

> openGauss 本身就支持 floatvector 列类型和 GSDiskANN 磁盘向量索引。一张表同时存结构化字段、文本、向量、BM25 索引，混合检索不需要跨系统。而且银行内网环境，少一个外部组件就少一个运维负担。GSDiskANN 是 openGauss 基于微软 DiskANN 自研的，我们配置了 1024 段 PQ、16 个聚类中心、L2 距离。

---

### 9. BGE-large 为什么选 1024 维？怎么微调的？

> 1024 是 BGE-large 模型的固定输出维度，不是我们选的——BGE 族有三个规格：small=512、base=768、large=1024。选 large 是因为去重后知识库十万级文档块，1024 维的判别力更强，精度收益大于存储开销。微调用了 10.6 万条 GaussDB 语料，包括产品文档、排障手册、历史工单，在银行内网完成——因为数据不能出内网。

---

### ★10. 向量检索和 BM25 怎么融合的？为什么是结果合并而不是加权？

**考察意图**：你是不是真理解两种检索的本质区别。

> 向量做语义匹配——"CPU 占用异常"能匹配"处理器使用率过高"。BM25 做精确命中——"gs_dump"这种专有名词向量覆盖不到。它们是互补关系，不是竞争关系。
>
> 为什么不用加权融合？因为向量相似度和 BM25 分数不在同一个尺度上，直接加权没意义。我们的做法是两路各自 Top-K，结果集合并去重后全部交给 reranker 重新打分，reranker 来做统一的尺度校准。

---

### 11. prev_uuid / next_uuid 是干嘛的？

> 检索命中片段经常从半截开始，LLM 看不懂。相邻块拼接就是利用 prev_uuid/next_uuid 指针把前后块也拉出来，拼成完整上下文再送给 LLM。

---

## 三、Agent 与工具调用（架构深度区）

### ★12. DeepSeek 的 Function Call 怎么用的？

**考察意图**：你是不是只会照着文档调 API，还是理解了原理。

> 没用原生 API。项目要支持 6 种模型，各自原生 function calling 行为不一致。我们设计了一个模型无关的两阶段方案：第一阶段，把 21 个工具的 name+description+参数 schema 拼成 JSON 放进 system prompt，让 LLM 选一个工具名。第二阶段，再给 LLM 这个工具的详细参数 schema，让它提取参数值。
>
> 盘古原生支持 function_call 的模型走原生路径更快，其他模型走纯 prompt 路径也能达到相同效果——接口是统一的。

---

### ★13. 为什么分两步而不是一步？

> 数学上是一个搜索空间问题。21 个工具 × 平均 3 个参数 = 63 维决策空间。一步让 LLM 在 63 维里找最优解，准确率只有 60%。拆开后第一步 21 维、第二步 3 维，难度降了一个数量级，准确率到了 95%+。

---

### ★14. 怎么保证 LLM 不会调错工具、填错参数？

**考察意图**：你是否考虑了容错和校验。

> 四层保障。第一层，prompt 约束——用结构化 JSON 描述工具接口。第二层，注册表校验——LLM 返回的工具名如果在 Registry 里不存在，直接拒绝。第三层，确定性参数校验——用 Python 的 inspect.signature 和函数签名比对，多的参数丢弃，缺的退回。为什么不用 prompt 约束？因为 prompt 是 99% 正确率，inspect 是 100%。在银行生产环境里，那 1% 就是事故。
>
> 第四层就是刚刚说的两阶段分离，把任务拆开了降低难度。

---

### 15. 为什么不用 LangGraph？

> 评估过。LangGraph 是自由探索式 Agent 图——LLM 动态决定下一步。但数据库故障诊断的核心约束是排查路径已知，不能自由探索。CPU 飙高→查指标→发现 IO 异常→查慢 SQL→查执行计划，这是 DBA 验证过的确定性路径。用 LangGraph 的 ConditionalEdge 让 LLM 决定下一步，可能跳过关键步骤或反复横跳。
>
> 我们的方案是诊断树引导的确定性管线——树节点是工具，树路径是验证过的排查序列。LangGraph 的 ConditionalEdge 在诊断场景是风险而非收益。

---

### 16. 工具注册系统怎么设计的？

> 自研的 Registry 装饰器模式。每个工具通过 `@base_tools(name=..., description=..., params=[Param(...)])` 注册。Registry 本质是一个增强版 dict，支持装饰器语法和角色权限控制。和 LangChain 的 @tool 思路上类似，但我们自己实现了完整的参数 schema 定义和校验体系。

---

### 17. 21 个工具具体有哪些？举个复杂工具的例子

> 涵盖指标监控、慢 SQL 诊断、锁检测、参数调优、告警管理等方向。比如 `risk_analysis`——需要 metric 名称（必填）和 warning_hours（可选），内部调用 DBMind 的时序预测 API，返回未来 N 小时的指标趋势。再比如 `slow_sql_rca`——从 pg_stat_activity 抓当前慢 SQL，解析执行计划，归类根因（统计信息过期 / 索引缺失 / 参数配置不当）。

## 四、安全与生产可靠性（落地深度区）

### ★18. 怎么保证大模型生成的运维操作安全可靠？

**考察意图**：你是真见过血的生产级思维，还是 toy project 思维。

> 核心设计哲学：LLM 是信息提取者，不是执行者。它输出的只是"建议"，必须经过确定性校验。
>
> 五层保障：第一层 DFA 前缀树，2 万+敏感词毫秒级拦截。第二层 XLNet 微调分类器，做语义级别的风险兜底。第三层工具注册表校验，LLM 输出的工具名不在注册表里就拒绝。第四层 inspect.signature 确定性参数校验。第五层数据库层——SQL 注入转义 + 密码 AES-256-CBC 加密存储。

---

### 19. DFA 敏感词检测具体怎么实现的？

> 用 Trie 树（前缀树），2 万多个敏感词。建立时每个词逐字符插入树节点，查询时 O(n) 遍历输入文本，只要走出了一条完整路径就命中。单次检测不到 1 毫秒。放在检索链路最前面——命中了直接返回固定话术，不进入后续流程。

---

### ★20. 上线后遇到过什么性能瓶颈？怎么解决的？

> 四个瓶颈。一是 LLM 推理延迟——完整回答要 10 秒，方案是 SSE 流式输出，首 token 200ms 就能看到反馈。二是向量检索——百万级文档全表扫描慢，方案是 GSDiskANN 磁盘索引 + PQ 压缩 + 30 并行。三是外部服务抖动——三层容错：HTTP 自动重试 3 次 + 函数级 retry 装饰器 + 启动时对所有服务做连通性预检。四是检索效率——LLM 调用本身最贵，所以在检索阶段 score<0 的直接丢弃，减少 LLM 输入长度，实测减少了将近一半。

---

### 21. 如果 LLM 服务挂了怎么办？

> 目前需要手动改配置切换备用模型，这是项目不足之一。理想做法是加一个健康检查+自动切换的中间层。我们之所以没做是因为银行内网环境服务本身就做了高可用，实际运行中 LLM 服务挂掉的概率很低。

---

## 五、系统设计思维（高段位追问）

### 22. 你觉得 GaussMaster 和 D-Bot、DB-GPT 的核心差异是什么？

> 最大差异是诊断树引导的多 Agent 协调。D-Bot 和 DB-GPT 是自由探索式——LLM 自己决定下一步调什么工具，这在简单场景灵活，但复杂场景不稳定。我们的诊断树是 GaussDB 专家预定义的——树节点是具体工具，树路径是验证过的排查管线。Agent 按路径走，交叉审查只在路径节点之间切换，稳定性和准确率明显优于自由探索。

---

### 23. 如果让你重新设计，会做什么不同的选择？

> 两个。一是 LLM 层的 fallback 机制——现在切换备用模型要手动改配置，应该做自动健康检查+切换。二是诊断树和 Agent 可以解耦得更彻底——让诊断树成为一个独立的知识表示层，Agent 只是执行器之一，这样换 Agent 框架不用重构诊断逻辑。

---

### ★24. 你觉得这个项目最大的不足是什么？

**考察意图**：看你能不能客观评价自己的工作。

> 除了刚刚说的 fallback 和耦合问题，还有一个是检索结果的缓存没做。HyDE 和查询改写的 LLM 调用是最慢的环节，如果缓存同义问题的改写结果，响应速度能进一步提升。另外用户的个性化也没做——不同用户的文档偏好、版本偏好应该学习，但现在所有用户共用同一套检索逻辑。

---

### 25. 为什么选择 FastAPI 而不是 Flask 或 Django？

> FastAPI 天然支持异步，我们的 LLM 调用、embedding 调用、向量检索全部是 IO 密集型操作，异步能显著提升并发吞吐。而且 FastAPI 自带 OpenAPI 文档生成，联调方便。至于 Flask——DBMind 早期用过，GaussMaster 立项时直接选了 FastAPI。

## 六、技术细节追问（手撕源码级）

### 26. 文档分块不是简单按字数切的是怎么切的？

> Markdown 是标题驱动的层次化分块——先用正则识别标题层级，每个块拼上完整的标题路径（比如"性能调优\nCPU诊断\n### 高CPU场景"），然后按 500 字阈值切。关键规则是代码块、表格、列表、引用不可分割——当前处于这些特殊区域内即使超 500 字也不切。
>
> DOCX 是三次分组——先按 Heading 1-9 分组，再按 Block Label 样式分组，最后按 500 字分组。表格转成"header1: value1, header2: value2"的结构化文本。

---

### 27. 去重是怎么做的？

> 每个块的文本内容做 MD5 哈希（`hashlib.md5(content).hexdigest()`），存为 `dup_uuid`。所有块按 dup_uuid 全局去重。相邻分块模式（有 overlap）下用的是"前块MD5+当前MD5+后块MD5"三块联合指纹——因为重叠区域会导致单块 MD5 无法正确去重。

---

### 28. openGauss 怎么连的？用的是什么驱动？

> 向量表用 psycopg2 直连——因为需要 floatvector 列类型、`<->` L2 距离操作符、GSDiskANN 索引，这些都是 openGauss 私有的，ORM 不支持。元数据表（交互记忆、诊断报告）用 SQLAlchemy ORM——因为不需要向量能力，ORM 管理更方便且可切换数据库类型。

---

### 29. 向量查询的 SQL 怎么写？

```sql
-- 向量检索（L2 距离）
SELECT * FROM gauss_kb 
ORDER BY text_vector <-> '[0.12, -0.34, ..., 0.56]' 
LIMIT 10;

-- 文本检索（BM25）
SELECT * FROM gauss_kb 
ORDER BY text ### 'CPU 使用率飙高' DESC 
LIMIT 10;
```

`<->` 是 L2 距离操作符，`###` 是 BM25 排序操作符——都是 openGauss 的 SQL 扩展。

---

### 30. GSDiskANN 索引的具体参数是什么？

```sql
CREATE INDEX ON gauss_kb 
USING gsdiskann(text_vector l2) 
WITH (
    pq_nseg=1024,      -- PQ 段数 = 嵌入维度
    pq_nclus=16,       -- 聚类中心数
    queue_size=100,    -- 搜索优先队列大小
    num_parallels=30,  -- 并行度
    enable_pq=true     -- 开启乘积量化
);
```

## 七、落地效果与数据（说服力题）

### 32. 85.23% 的 QA 高质量率是怎么评估的？

> 混合评估——人工 + LLM 作为评判者。评估维度是相关性、准确性、安全性。400 多道题来自银行真实场景，覆盖产品查询、性能故障排除和异常诊断。

### ★33. 如果线上模型给出错误诊断怎么办？

**考察意图**：你有没有考虑过容错和兜底。

> 多层设计来降低这个风险。第一，工具调用不是直接操作数据库——21 个工具大部分是只读的监控诊断类，少数写操作需要额外确认。第二，所有 QA 记录都带用户反馈机制（点赞/点踩/举报），错误诊断会被标记和复盘。第三，诊断树路径是专家验证过的，Agent 按路径走比自由探索稳定。但如果真出了错误诊断，目前还是需要人工复核——这也是未来需要改进的方向。

## 八、内核衔接（转行叙事题）

### ★34. 为什么从内核转到 AI 应用？

**考察意图**：全场最重要的问题。你是不是逃兵。

> 做 GaussMaster 的时候我发现一件事：AI 应用最难的不是模型，是怎么把模型和已有的复杂系统可靠地接起来。数据库内核我做了四年，成长曲线在放缓。但 AI 应用领域还非常早期，大部分做 AI 的人没有底层系统经验，做出来的东西在工程上站不住。我觉得这是我差异化最大的地方——我能把一个 AI 系统从头到尾踩实了落地。不是觉得内核不好，是我在这个方向上能做出的增量更大。

---

### ★35. 内核经验对 AI 应用开发有什么帮助？

> 三个层面。工程习惯上——内核开发对正确性要求 100%，我带过来的习惯是对 prompt 输出做确定性校验而不是靠信仰。系统感知上——做慢 SQL 诊断时我知道 pg_stat_activity 是快照、有采样窗口，这些知识决定了工具接口怎么设计，LLM 回答不出这些。性能敏感度上——内核开发习惯了 O(n²) 思维，在做 embedding 批处理和索引构建时直接复用。

---

### 36. 你在内核具体做什么？

> 查询诊断和可观测性。慢 SQL 的诊断链路——从 pg_stat_activity 采集到执行计划反解析到根因归类。指标采集框架——把采集延迟从秒级降到毫秒级。系统表优化——pg_stat_statements 的哈希表扩展策略调整。
