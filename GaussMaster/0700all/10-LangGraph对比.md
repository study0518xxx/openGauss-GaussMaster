# 10 - LangGraph 对比：为什么不用

## 先确认你懂 LangGraph

LangGraph 是 LangChain 出的**有状态多步 Agent 编排框架**，核心概念：

```
StateGraph(Node, Edge, ConditionalEdge)
    ↓
每个 Node = 一个处理单元（LLM调用 / 工具执行 / 代码逻辑）
Edge = 确定性流转
ConditionalEdge = LLM根据当前状态动态决定下一步走哪个Node
    ↓
典型模式：agent → tool → agent → tool → ... → final answer
```

它解决的核心问题：Agent 执行是一个**有状态的多步循环**，不是一次函数调用。LangGraph 把这个循环建模成图，支持 checkpoint 恢复、分支、并行。

---

## 面试官问这个的真实意图

他不在考你"知不知道 LangGraph"，在验证两件事：

1. **你做技术选型时有没有调研过 LangGraph**（没调研 = 视野窄）
2. **你的自研方案是不是 LangGraph 能替代的**（能替代 = 你重复造轮子）

---

## 答案

> 评估过。LangGraph 本质是一个**自由探索式的 Agent 图**——LLM 在每一步根据当前状态动态决定下一步走哪个节点。这个模式在开放域问答或者通用 Agent 场景下很好用。
>
> 但 GaussMaster 的场景不一样。数据库故障诊断有一个核心约束：**排查路径是已知的，不能自由探索。** CPU 飙高 → 先查指标 → 发现 I/O 异常 → 再查慢 SQL → 再查执行计划——这是一条被 DBA 验证过的确定性路径。如果用 LangGraph 的 ConditionalEdge 让 LLM 决定下一步，它可能跳过关键步骤，或者在两个节点间反复横跳。
>
> 所以我们的方案不是图探索，是**诊断树引导的确定性管线**——树节点是工具，树路径是验证过的排查序列。Agent 不是自由探索者，是按图索骥的执行者。这种模式下，LangGraph 的 ConditionalEdge 反而会增加不确定性，我们需要的确定性路由 LangGraph 是支持的但它的核心价值（动态决策）我们没用到。
>
> 还有一点，LangGraph 的 Node 抽象粒度偏粗——一个 Node 是一次 LLM 调用。我们做的是两阶段工具调用（选工具 + 填参数分离），这拆成两个 Node 的话状态传递反而复杂了，不如一个函数调用链直接。

---

## 关键对比

| LangGraph 适合 | GaussMaster 不需要 |
|---------------|-------------------|
| LLM 动态决定下一步 | 诊断路径是预先验证过的 |
| 探索式工具调用 | 确定性工具序列 |
| 通用 Agent 编排 | 数据库诊断专用 |
| Node 粒度 = 一次 LLM 调用 | 两步分离需要更细粒度 |

---

## 如果被追问"什么时候该用 LangGraph"

> 开放域的、没有标准操作流程的场景——比如通用的代码助手、客服对话、多轮信息收集。这些场景你不知道用户下一步会说什么、需要哪种工具，让 LLM 动态路由是最优解。
>
> 但数据库诊断不是——34 个根因场景的排查路径已经被 DBA 验证过了，这时候动态路由只会引入不确定性。我们的诊断树方案本质上是把"LLM 动态决策"替换为"专家预定义路径 + LLM 信息提取"，这在故障诊断场景下准确率和稳定性都更高。

---

## GaussMaster 的自研替代方案

```
LangGraph 的做法：
  agent_node → conditional_edge → tool_node → agent_node → ...

GaussMaster 的做法：
  诊断树匹配 → 树路径展开 → 
    阶段1: LLM选工具 → 阶段2: LLM填参数 → inspect校验 → 执行 → 结果反思
    → 下一个树节点（确定性路由，不需要LLM决策）
```

核心差异：**下一步做什么不是 LLM 决定的，是诊断树预定义的。** LLM 的角色从"决策者"降为"信息提取者"。
