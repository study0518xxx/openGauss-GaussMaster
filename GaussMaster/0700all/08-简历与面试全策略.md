# 08 - 简历与面试全策略

## 一、简历上写几个项目

**两个，不要三个。**

- **GaussMaster**（AI 应用，10-12 个月）—— 主打，占面试 60% 时间
- **openGauss 内核开发**（2021.06 - 至今）—— 证明深度，占 25% 时间

不加个人项目。两个项目已经构成了清晰叙事："四年内核 → 顺势转型 AI 应用"。加第三个反而分散注意力、暴露凑数痕迹。

### 时间重叠怎么写

```
openGauss 数据库内核开发                    2021.06 - 至今
openGauss-GaussMaster（AI 运维 Copilot）    2024.06 - 2025.06
```

直接写，不用解释。两个项目是包含关系（GaussMaster 本身就是 openGauss 生态的项目），不是冲突关系。

如果被追问"时间怎么分配"：
> GaussMaster 是社区项目，前期大概 30% 时间做架构讨论和工具接口设计，后期核心开发阶段提高投入。两个项目在 openGauss 生态内，很多技术积累是复用的，切换成本很低。

### 项目时长

GaussMaster 说 **10-12 个月**，分三段：
- 2024.06 - 2024.09：调研 + 工具接口设计（内核经验主导）
- 2024.10 - 2025.03：AI 应用核心开发（RAG 管道 + Agent 链路）
- 2025.04 - 2025.06：银行 POC 部署 + 论文

## 四、面试官会怎么问

### 面试官的核心焦虑只有两个

1. **你的 AI 项目到底有多深？**（怕你是挂名打杂）
2. **你离了内核能不能干活？**（怕你只会 C，写不了 Python 工程）

所有问题都在验证这两件事。

### 10 道高频题 + 应对思路

**Q1："介绍一下 GaussMaster 这个项目"**
> 不要说"这是一个基于 LLM 的数据库 Copilot..."——这是背 README。要说你**为什么做、负责什么、难点在哪**。

**Q2："为什么不用 LangChain？"**
> 三个原因：检索器不支持三路混合、没有 openGauss 的 vectorstore 集成、AgentExecutor 的 ReAct 循环在数据库诊断场景不够可控。

**Q3："检索管道具体怎么做的？"**
> 四阶段：安全检测 → 混合检索（向量+BM25）→ 重排序 → 生成。重点讲降级策略（HyDE + 查询改写）。

**Q4："向量数据库为什么不用 Milvus？"**
> openGauss 自带 floatvector + GSDiskANN + BM25，一张表搞定混合检索，免去跨系统同步。

**Q5："DeepSeek 的 Function Call 怎么用的？"**
> 没用原生 API。设计了模型无关的两阶段方案：先选工具名，再填参数。准确率从 60% 提升到 95%。

**Q6："怎么保证 LLM 不调错工具？"**
> 四层保障：Schema 约束 → Prompt 引导 → inspect.signature 校验 → 两阶段分离降低难度。

**Q7："为什么不用 LangGraph？"**
> LangGraph 是自由探索式 Agent 图，数据库诊断需要确定性路径。诊断树引导的方案在故障诊断场景准确率更高。

**Q8："你在内核做什么？"**
> 不要答"慢 SQL 诊断、指标采集"太抽象。说"负责查询诊断和可观测性，把采集延迟从秒级降到毫秒级"。

**Q9："为什么从内核转到 AI 应用？"**
> 这是全场最关键的问题。回答不好直接挂。**不要说是逃兵，要说"我能做出的增量更大"。**

**Q10："内核经验对 AI 应用有什么帮助？"**
> 三个层面：工程习惯（对正确性零容忍）、系统感知（知道工具接口底下是什么）、性能敏感度（O(n²) 思维带到 embedding 批处理）。

### 全场核心定位

> "我是做过内核的人里最懂 AI 应用的，也是做 AI 应用的人里最懂底层系统的。"

## 五、自我介绍模板（2 分钟）

> 我在 openGauss 做了四年数据库内核开发，主要负责查询诊断和可观测性模块。期间参与了 GaussMaster 这个 AI 项目——用 LLM 做数据库的智能运维，我负责 RAG 检索管道和 Agent 工具链路两个核心模块。
>
> 这个项目让我发现一个事：AI 应用落地的难点往往不在模型本身，而在于怎么把模型和已有的复杂系统可靠地接起来。我四年的内核经验在这方面是很大的优势——理解底层系统的人做 AI 应用，能从头到尾把东西踩实。
>
> 现在项目已经在银行生产环境跑了，34 个运维场景零人工干预。我接下来想找一份更专注做 AI 应用的工作，把这个方向做深。

## 六、行为问题速答

| 问题 | 要点 |
|------|------|
| 最大挑战 | 多模型 Function Call 统一适配——不靠原生 API，设计统一两阶段方案 |
| 最大不足 | LLM 层的 fallback 机制不够完善；诊断树和 Agent 耦合偏紧 |
| 和其他项目区别 | D-Bot/DB-GPT 是自由探索式，我们是诊断树引导的确定性管线 |
| 重新设计会做什么不同 | 完善 fallback 自动切换；诊断树和 Agent 彻底解耦 |
