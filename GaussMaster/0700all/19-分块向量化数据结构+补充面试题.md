## 一、分块逻辑：代码逐行讲透

### 1.1 整体流程（split_util_md.py）

```
原始 Markdown 文本
  │
  ├─ ① preprocess_md_content()  ← 标记所有不可分割的结构
  │     ├─ tag_list_block()     列表/有序列表 → ￥￥LIST￥￥包裹
  │     ├─ tag_quote_block()    引用块       → ￥￥QUOTE￥￥包裹
  │     ├─ find_code_partion()  代码块       → ￥￥CODE￥￥包裹
  │     ├─ extract_table()      HTML/竖线表格 → ￥￥TABLE￥￥包裹 + 结构化文本
  │     ├─ clean_link()         链接 → 只留文字，丢掉URL
  │     ├─ clean_html_tag()     去掉所有 <tag>
  │     ├─ tag_title()          每个 #标题前 → 插入 ￥￥TITLE￥￥
  │     └─ clean_text_font()    **粗体** *斜体* ~~删除线~~ → 只留字
  │
  ├─ ② split by TITLE_IDENTIFIER  ← 按标题切成段
  │
  ├─ ③ 对每个标题段 → get_title_info() 拿到标题级别
  │     #      → 级别1
  │     ##     → 级别2
  │     ###    → 级别3
  │
  ├─ ④ get_title_contents() → 组装标题路径前缀
  │     content_titles = []   ← 一个栈，记录当前标题路径
  │     遇到 #性能调优    → content_titles = ["性能调优"]
  │     遇到 ##CPU诊断    → content_titles = ["性能调优", "CPU诊断"]
  │     遇到 ###高CPU场景 → content_titles = ["性能调优", "CPU诊断", "高CPU场景"]
  │     prefix_title = "性能调优\nCPU诊断"   ← 拼成前缀字符串
  │
  ├─ ⑤ split_title_text(prefix_title, 标题内容) → 按长度二次切分
  │     关键规则：代码/表格/列表/引用/参数区域内 → 不切！
  │
  └─ ⑥ delete_duplication_prefix() → 清理重复的标题前缀
```

### 1.2 预处理：10 种正则模式识别 Markdown 结构

```python
TITLE_PATTERN       = r'^#{1,6}\s(.+)'         # # → ###### 标题
LIST_PATTERN        = r'^[-*+](\s+)'            # - * + 开头
ORDER_LIST_PATTERN  = r'^\d+\.(\s+)'            # 1. 2. 开头
QUOTE_PATTERN       = r'^>{1,3}'               # > 引用
CODE_PATTERN        = r'```[\s\S]*?```'         # 代码块
TABLE_PATTERN        = r'<table[^>]*>[\s\S]*?</table>'  # HTML表格
VERTICAL_TABLE      = r'(\|-{1,2})+\|'          # |---| 竖线表格
LINK_PATTERN        = r'!*\[([^\]]*)\]\([^\)]*\)'  # [文字](url)
ITALIC_PATTERN      = r'\*([\S]+.*?[\S]+|\S)\*'
BOLD_PATTERN        = r'\*{2}([\S]+.*?)\*{2}'
STRIKEOVER_PATTERN  = r'~{2}([\S]+.*?[\S]+|\S)~{2}'
```

### 1.3 为什么用全角￥做标记符

```python
TABLE_IDENTIFIER  = "￥￥￥￥￥TABLE￥￥￥￥￥"
TITLE_IDENTIFIER  = "￥￥￥￥￥TITLE￥￥￥￥￥"
LIST_IDENTIFIER   = "￥￥￥￥￥LIST￥￥￥￥￥"
CODE_IDENTIFIER   = "￥￥￥￥￥CODE￥￥￥￥￥"
```

不用 ASCII 标记（如 `<CODE>`）是因为文档正文里可能出现 `<CODE>` 字样。全角 `￥` 在技术文档正文中出现概率几乎为零，不会误匹配。

### 1.4 代码块保护：先分离再处理

```python
def preprocess_md_content(md_content):
    md_content = tag_list_block(md_content)     # ① 先标记列表
    md_content = tag_quote_block(md_content)    # ② 先标记引用
    code_partion = find_code_partion(md_content) # ③ 找出所有代码块位置 [start, end]
    
    # ④ 只对"代码块之外"的区域做文本清洗
    for l, r in code_partion:
        if c_index < l:
            # 这一段不在代码块内 → 做表格/链接/标签/标题处理
            link_content = text_split_without_code(md_content[c_index:l])
            res_content += link_content
        # 代码块内原样保留
        res_content += CODE_IDENTIFIER + '\n'
        res_content += md_content[l:r]
        res_content += '\n' + CODE_IDENTIFIER
```

**为什么这样设计**：代码块里的 `#` 是注释不是标题，`<table>` 是代码不是表格。先分离代码块，就不会把代码内容误处理。

### 1.5 HTML 表格转结构化文本

```python
# 原 HTML:
# <table>
#   <tr><th>参数</th><th>说明</th></tr>
#   <tr><td>metric</td><td>指标名称</td></tr>
# </table>

# 处理后:
# ￥￥TABLE￥￥
# 参数: metric, 说明: 指标名称;
# ￥￥TABLE￥￥
```

处理函数 `deal_table()` 逐行提取 `<th>` 表头和 `<td>` 数据，转成 `header: value` 格式，用 `;` 分隔行。这样 LLM 能理解表格的语义（表头和数据的关系）。

### 1.6 长度切分的状态机

```python
def split_title_text(prefix, title_content):
    table_status = False    # 当前在表格内？
    list_status  = False    # 当前在列表内？
    code_status  = False    # 当前在代码块内？
    quote_status = False    # 当前在引用内？
    param_status = False    # 当前在参数说明内？
    
    for line in lines:
        # 只有当不在任何特殊区域时，才能按长度切
        if not (code_status or table_status or list_status or quote_status or param_status) \
                and block_length > 500:
            # 切！输出当前块，开始新块
            content_list.append(prefix + '\n' + clean_tag_info('\n'.join(block_list)))
            block_list = [line]
            block_length = 0
        else:
            # 不切！继续追加
            block_list.append(line)
            block_length += len(line)
        
        # 状态切换：遇到标记符翻转状态
        if line == LIST_IDENTIFIER:   list_status = not list_status
        elif TABLE_IDENTIFIER in line: table_status = not table_status
        elif CODE_IDENTIFIER in line:  code_status = not code_status
        ...
```

**就像一个红绿灯**：普通文字区是绿灯（可以切），特殊区域是红灯（不许切）。`￥￥` 标记符就是切换红绿灯的开关。

### 1.7 最后一块的合并逻辑

```python
if block_list:
    last_block = clean_tag_info('\n'.join(block_list))
    if block_length < 200 and content_list:
        # 太短（<200字）→ 拼到前一块后面
        content_list[-1] += '\n' + last_block
    else:
        # 够长 → 独立成块
        content_list.append(prefix + '\n' + last_block)
```

### 1.8 相邻分块模式（带重叠）

```python
# 用途：需要上下文重叠的场景
separators = ["\n\n", "\n", " ", ""]
content_list = recursive_split_text(p_content, separators, 384, 75)
# chunk_size=384, chunk_overlap=75（约20%重叠）
```

按分隔符优先级递归切分：双换行 > 单换行 > 空格 > 字符。相邻块之间有 75 字的重叠，保证 LLM 不会因为边界截断而看不懂上下文。

## 二、向量化：代码逐行讲透

### 2.1 向量服务封装

```python
# retriever_util.py:50-84
class OnlineEmbedding():
    def __init__(self, url, ssl_context):
        self.url = url       # HTTP 服务地址
    
    def get_embedding_dimensions(self):
        return 1024          # 固定 1024 维

    async def __embedding(self, queries):
        data = {"query": queries}
        # HTTP POST → 独立嵌入服务 → 返回 [[0.12, -0.34, ..., 0.56], ...]
        response = session.post(url=self.url, data=json.dumps(data))
        return response.json()
```

**不是把 BGE 模型加载到 GaussMaster 进程里**，是独立部署的 HTTP 服务。这样模型升级不重启主服务，嵌入服务和检索服务独立扩缩容。

### 2.2 入库时的向量化：逐条文本 → 1024 个浮点数

```python
# gaussdb_vector.py:307-332
async def _doc_to_db_string(self, doc):
    value = []
    embedding_list = []
    
    for field in self.fields:
        f_content = doc.metadata.get(field, '')   # 拿文本字段内容
        value.append(escape_single_quote(str(f_content)))
        
        if field in self.embedding_keys:          # 这个字段需要向量化
            # HTTP 调嵌入服务 → 拿回 1024 个浮点数
            embedding = await self.embedding_function.query_embedding(f_content)
            embedding_str = [str(num) for num in embedding]
            embedding_list.append(embedding_str)
    
    # 拼 INSERT SQL: ('uuid','title','text',...,'[0.12,-0.34,...,0.56]')
    insert_string = "('" + "','".join(value) + "'"
    for emb in embedding_list:
        insert_string += ",'[" + ",".join(emb) + "]'"
    insert_string += ")"
    return insert_string
```

**注意**：向量以字符串形式拼进 SQL，openGauss 收到后自动转成 `floatvector(1024)` 列类型。

### 2.3 批量入库：每 1000 条提交一次

```python
# gaussdb_vector.py:334-350
async def _batch_insert(self, docs):
    sql = f'INSERT INTO "{self.db_index}" VALUES'
    count = 0
    values = []
    for doc in docs:
        cur_value = await self._doc_to_db_string(doc)   # 逐个向量化
        values.append(cur_value)
        count += 1
        if count % 1000 == 0:
            # 攒够 1000 条 → 一次性 INSERT
            cur_sql = sql + ','.join(values)
            self.cur.execute(cur_sql)
            values = []    # 清空，继续下一批
    # 最后不足 1000 条的尾巴也提交
    if values:
        cur_sql = sql + ','.join(values)
        self.cur.execute(cur_sql)
```

**为什么是 1000 条一批**：单条 INSERT 每次都是一次事务，1000 条一批把事务开销摊薄到 1/1000。

### 2.4 建表：包含向量列

```python
# gaussdb_vector.py:118-131
def get_fields_with_vector(self, embedding_keys, dimension):
    fields = []
    for field in self.fields:
        if field in self.serial_field:
            fields.append(f'"{field}" serial')
        else:
            fields.append(f'"{field}" TEXT')
    for embedding_key in embedding_keys:
        # ← 这里是向量列
        fields.append(f'"{embedding_key}_vector" floatvector({dimension})')
    return ','.join(fields)
```

生成的建表 SQL：

```sql
CREATE TABLE gauss_kb (
    uuid TEXT,
    title TEXT,
    text TEXT,
    ...
    text_vector floatvector(1024)    -- ← 1024 维向量列
) with (orientation=ROW, storage_type=astore);
```

### 2.5 查询时的向量检索

```python
# gaussdb_vector.py:177-198
async def search_vector(self, query, topk):
    # ① 用户问题 → 嵌入服务 → 1024 维向量
    embedding = await self.embedding_function.query_embedding(query)
    embedding_str = [str(num) for num in embedding]
    query_sql = "'[" + ",".join(embedding_str) + "]'"
    
    # ② L2 距离排序，GSDiskANN 索引加速
    sql = f'SELECT * FROM "{self.db_index}" '
    sql += f'ORDER BY "{embedding_key}_vector" <-> {query_sql} LIMIT {topk}'
```

`<->` 是 openGauss 的 L2 距离操作符，GSDiskANN 索引自动加速。

## 四、补充面试题 20 道

### 分块相关

**Q1：为什么用全角￥做标记符而不是 ASCII？**
> 全角￥在技术文档正文中出现概率几乎为零。用 `<CODE>` 做标记的话，文档正文里可能就有 `<CODE>` 字样，会误匹配。

**Q2：代码块里的 `#` 怎么处理？**
> 先分离代码块，只对代码块之外的区域做标题识别。代码块内容原样保留。

**Q3：如果一段文字 800 字且全是列表，你们怎么切？**
> 不切。列表区域被 ￥￥LIST￥￥ 包裹，split_title_text 检测到 list_status=True，即使超过 500 字也不切。

**Q4：DOCX 和 Markdown 的分块逻辑有什么不同？**
> Markdown 是标题驱动的层次化分块，DOCX 是按 Heading 样式 + Block Label + 长度三次分组。DOCX 表格转成 `header: value` 结构化文本。

**Q5：相邻分块模式（带 overlap）什么时候用？**
> 需要相邻块之间有上下文重叠的场景。块大小 384 字，重叠 75 字（约 20%）。

### 向量化相关

**Q6：为什么向量化服务不嵌入到 GaussMaster 进程里？**
> 独立部署可以独立扩缩容。模型升级不重启主服务。多服务可共享同一个嵌入服务。

**Q7：向量入库是同步还是异步？**
> 入库是异步的（async/await），因为 HTTP 调用嵌入服务是 IO 密集型。但批量 INSERT 到 openGauss 是同步的（psycopg2 不支持异步）。

**Q8：如果嵌入服务调用失败怎么办？**
> 三层容错：HTTP 层 3 次重试 + 启动时连通性预检 + 嵌入服务本身做高可用。

**Q9：为什么是 1024 维而不是 768 维？**
> BGE-large 的固定输出维度。选 large 而不是 base（768维），因为知识库十万级文档块，1024 维的判别力更强。

**Q10：向量存在数据库里是什么格式？**
> openGauss 专有的 `floatvector(1024)` 列类型。1024 个 float32 数字用一个紧凑的二进制格式存储。

### 工具相关

**Q11：如果 21 个工具里有两个功能相似的，LLM 怎么区分？**
> 靠 description 字段区分。每个工具的 description 都详细描述了功能和适用场景。如果 LLM 选错了，Registry 校验会通过（因为两个工具都存在），但参数校验会失败（参数 schema 不同），或者结果不对。

**Q12：新加一个工具要改哪些地方？**
> 加一个 `@base_tools` 装饰的函数就行。Registry 自动注册，infer_tool_name 自动感知（因为它是动态读取 Registry 的 detail_str_list）。不需要改任何其他代码。

**Q13：inspect.signature 校验具体能抓到什么问题？**
> LLM 多给了不存在的参数（丢弃）、LLM 漏了必填参数（提示用户补充）、LLM 给了错误类型的参数（Python 运行时报错，但概率极低，因为 prompt 里声明了类型）。

**Q14：为什么不用 LangChain 的 BaseTool？**
> 我们需要参数级别的精确控制——Param 类定义了 name、type、required、default_value，是为了生成两种格式（文本和 JSON）给不同模型用。LangChain 的 BaseTool 没有这个能力。

### 系统相关

**Q15：为什么 FastAPI 的路由不用原生的 @app.post，而是自己包了一层 HttpService？**
> 解耦。HttpService 是 DBMind 时期从 Flask 迁移到 FastAPI 时设计的抽象层。将来想再换框架，只改 HttpService 的底层实现，不改业务代码。

**Q16：为什么 qa_record 和 tb_interaction_memory 不合并？**
> 它们是两条独立代码路径各自带的表。RAG 用 psycopg2 连向量库顺手写 qa_record，Agent 用 SQLAlchemy 连 MetaDatabase 顺手写 tb_interaction_memory。技术上讲可以合并，但当时开发节奏没往这个方向优化。

**Q17：服务重启后，正在进行的工具调用会丢吗？**
> SESSION_TOOL_HISTORY 在内存里会丢。但丢的影响是下一轮重新让 LLM 推断一次工具名，不会导致数据错误。对话历史存在 tb_interaction_memory 里，重启后在 get_qa_history 里自动回填。

**Q18：系统有没有做限流？**
> 应用层没做。银行内网环境用户是 DBA 团队，并发可预测。Nginx 层做了基础的连接数限制。

**Q19：有没有做 A/B 测试？**
> 没做。银行 GPU 资源跑一套 38B 模型已经比较紧张。如果要做，会考虑在 API 网关层做流量分割——10% 请求走新模型，90% 走旧模型。

**Q20：这个系统最大的架构遗憾是什么？**
> 诊断树和 Agent 的耦合偏紧。理想情况诊断树是独立的知识表示层，Agent 只是执行器之一。现在换 Agent 框架需要同时改诊断树逻辑。
