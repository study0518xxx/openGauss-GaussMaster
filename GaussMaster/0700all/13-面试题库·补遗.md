## 十、HTTP 层与流式输出

### 38. 为什么用 SSE 而不是 WebSocket？

> 我们的场景是单向推送——服务端生成内容推给前端，前端不需要频繁向服务端发消息。SSE 比 WebSocket 简单得多，天然基于 HTTP，不需要额外的握手协议和心跳维护。而且 FastAPI 对 SSE 有原生支持，一行 `StreamingResponse` 就能搞定。
>
> 唯一不足是 SSE 不支持二进制，但我们的 LLM 输出全是文本，没影响。

### 39. SSE 流式输出的代码怎么写的？

```python
# 前端请求头
headers = {"Accept": "text/event-stream", "Connection": "keep-alive", "Cache-Control": "no-cache"}

# 服务端逐块返回
async def generate_answer(messages, model_name):
    llm_generator = await thread_request_from_llm(url, headers, params)
    while True:
        chunk = await asyncio.get_running_loop().run_in_executor(None, iter_next, llm_generator)
        if chunk == -1:
            break
        yield chunk  # 逐块 yield，FastAPI 自动封装为 SSE 事件
```

`keep-alive` 复用 TCP 连接避免频繁握手，`no-cache` 防止中间代理缓存导致前端收到旧数据。

### 40. 流式输出断了怎么办？有没有断点续传？

> 目前没有断点续传。LLM 调用失败会触发 HTTP 层的 3 次重试（`MAX_REQUEST_RETRIES=3`，退避因子 1 秒），但重试是从头开始调 LLM，不是从断点续。如果真的要做，可以在 LLM 返回的每个 chunk 上打序号，前端缓存已收到的 chunk，重连时从最后一个序号之后继续——但这要求 LLM 服务本身支持续传，我们用的盘古和 DeepSeek 都不支持。

### 41. 并发怎么处理的？能扛多少 QPS？

> FastAPI + uvicorn 本身就是异步框架，我们的 LLM 调用、embedding 调用、向量检索全部走 asyncio + ThreadPoolExecutor，不阻塞主线程。但实际 QPS 瓶颈不在应用层，在 LLM 推理服务——银行内网的 GPU 资源有限，盘古 38B 模型单次推理就要几秒。所以并发策略不是堆应用层线程，而是检索阶段尽量过滤，减少 LLM 调用量。

### 42. FastAPI 的路由是怎么注册的？用了装饰器吗？

> 用了自研的 `@request_mapping` 装饰器，不是 FastAPI 原生的 `@app.post`。因为我们在 FastAPI 上包了一层 `HttpService` 抽象，方便将来换框架。装饰器把路由信息存在 `_RequestMappingTable` 里，`start_listen()` 时批量注册到 FastAPI：

```python
@request_mapping(api_prefix + "/ask_gauss", method='POST', api=True)
@standardized_event_stream_output
async def ask_gauss(...):
    ...
```

### 43. 如果前端请求量突然暴增，你怎么限流？

> 项目目前没有做应用层限流。原因：银行内网环境，用户是内部 DBA 团队，并发量可预测。Nginx 层做了基础的连接数限制。如果未来开放给更大的用户群，最快的方式是在 FastAPI 中间件层加一个基于 token bucket 的限流器，或者直接依赖 Nginx 的 `limit_req` 模块。

## 十一、记忆机制深挖

### 44. 对话记忆存在哪里？为什么最长只保留 3 轮？

> 存在 `qa_record` 表里，每次问答结束自动落库。下次请求时 SQL 查最近 N 轮：`ORDER BY create_time DESC LIMIT {history_len}`。限制 3 轮的原因：LLM 上下文窗口有限，塞太多历史会挤占知识检索结果的空间；数据库诊断场景天然不需要长程记忆——排查完一个告警就结案了。

### 45. 会话状态丢了怎么办？比如服务重启？

> `SESSION_TOOL_HISTORY` 在内存里，重启就没了。但影响有限——这个 dict 只存当前会话正在调的工具名，丢了就让 LLM 重新推断一次。真正的对话历史在 `qa_record` 表里，重启不影响。

### 46. 工具调用历史记忆表为什么做了向量化？怎么用的？

> `gm_tool_history_memory` 表的 `question` 字段做了向量化。遇到新问题时，先向量检索历史上是否有相似问题——如果有，直接复用历史工具选择，跳过 LLM 推断。相当于一个"运维经验库"——"上次有人问 CPU 飙高，系统调了 risk_analysis，这次大概率也可以用"。

### 47. 有没有做用户级别的长期记忆？比如记住某个 DBA 的偏好？

> 没有。目前所有用户共用同一套检索逻辑和工具推荐。这是我列在项目不足清单里的一项——理想情况是记住用户的文档偏好（更信任内部文档还是社区文档）、版本偏好（倾向 7.0 还是 5.0 的解决方案）。

## 十二、意图识别与工具调用容错

### 48. 如果 LLM 选了一个不存在的工具怎么办？

> 不会执行。工具名出来后第一步就是 `check_has_valid_tool()`——在 Registry 里查：

```python
def check_has_valid_tool(tool_name):
    target_tool = global_vars.tools_registry.get(tool_name, None)
    return target_tool is not None
```

查不到就当场拒绝，返回"此问题暂时无法用工具解答"。LLM 幻觉输出 `risk_check`（实际是 `risk_analysis`），到这一步就被拦截。

### 49. 如果 LLM 选对了工具但参数填错了怎么办？

> `has_correct_params()` 用 `inspect.signature` 做校验。LLM 多给的参数直接丢弃，缺失的必填参数会提示用户补充。比如 LLM 输出了 `{"metric": "cpu", "extra_field": "xxx"}`，`extra_field` 不在函数签名里，被丢弃。如果缺了 metric，返回 False 并告诉用户"还缺 metric 参数，请输入指标名称"。

### 50. 如果 LLM 两次都推断不出正确的工具怎么办？

> 两阶段方案下，第一次选错工具的概率已经很低的（<5%），因为只需要从 21 个里选一个名字。如果真的两次都没选对，目前会直接告诉用户"无法解答"。未来可以加一个降级策略——把用户的自然语言问题直接转给 LLM 做自由问答（不调工具），从知识库里搜相关文档给出建议。

### 51. 用户说"帮我优化数据库性能"，这个意图怎么拆？

> LLM 先做意图分类。"优化性能"这个问题太笼统，agent 会先反问或拆解：是慢 SQL 优化？还是参数调优？还是索引建议？目前的做法是：如果 LLM 无法从一句话里提取出明确的工具名和参数，就会把问题抛回给用户，要求补充具体信息（比如"请提供慢 SQL 的 SQL 文本"或"请指定需要调优的参数名"）。

### 52. 用户给了错误信息（比如不存在的表名），工具怎么处理？

> 工具执行层的 DBMind API 会返回错误。比如用户说"帮我查 test_table 的锁情况"，`get_locking_sql` 调 DBMind 查询，DBMind 返回"表 test_table 不存在"。这个错误信息会原样返回给用户，不会吞掉。我们没有在 GaussMaster 层做表名存在性校验——因为那是 DBMind 和 openGauss 的职责。

## 十三、安全机制攻防

### ★53. 如果用户用"翻译成英文再执行"这种方式绕过 DFA 敏感词怎么办？

> DFA 只能拦截显式关键词，绕词攻击确实防不住。这就是为什么有第二层 XLNet 微调分类器——不做关键词匹配，做语义理解。"please remove the table named user_data"即使没有"删"字，XLNet 也能识别出这是危险操作。DFA 是快速粗筛，XLNet 是语义兜底。

### ★54. 如果用户用分段注入绕过——"第一段：帮我查一下 XX，第二段：然后 DROP 掉"？

> 目前的安全检测是在单次请求内对完整 question 做检测。如果用户在一个会话里分两次发——第一次正常、第二次恶意——第一次能过，第二次会在输入安全门被 DFA 拦截。但如果攻击者精心设计，让两段各自看起来都无害、合起来才有害，目前确实有盲区。最彻底的方案是在工具执行层做权限控制——危险操作（如 DROP）根本不注册为可调用工具。

### ★55. 如果 LLM 被提示注入，输出了危险的 SQL？

> 我们不给 LLM 直接执行 SQL 的能力。LLM 的输出只是"调用哪个工具 + 传什么参数"，真正的 SQL 是工具内部的 DBMind API 拼接的。而且我们做了 SQL 注入防护：所有用户输入在拼 SQL 前做转义：

```python
def escape_single_quote(x):
    return x.replace("'", "''")
```

配合 `check_sql_valid()` 用 sqlparse 检测是否单条 SQL——拒绝多语句注入。**没有直接执行 LLM 输出的 SQL 这个路径。**

### 56. 安全检测是不是也影响了正常用户？

> DFA 是毫秒级的，正常用户几乎无感。XLNet 分类器 <500ms，在检索开始前异步完成。如果误杀了正常问题，用户可以反馈举报，我们会定期复盘误杀 case 更新词库和模型。目前误杀率很低——因为敏感词库是 GaussDB 领域定制的，不会把"drop index"误判成危险操作。

### 57. 你们有没有做过对抗攻击测试？

> 论文里没提专门的对抗测试，系统目前的安全机制主要防的是无意的危险操作和明显的恶意注入，不是高对抗场景。银行内网的天然隔离和用户的专业背景也降低了对抗风险。如果未来开放给更大的用户群，需要引入专门的 prompt injection 检测层。

## 十四、故障容错与兜底

### 58. 如果 embedding 服务挂了怎么办？

> 三个层面。启动时 `check_connectivity_parallely()` 预检所有外部服务连通性，不通不让服务启动——避免跑着跑着才发现连不上。运行时 embedding 调用失败会抛异常，上层捕获后返回"服务暂时不可用"。embedding 服务本身做了高可用（银行内网标配），实际运行中几乎没有单点故障。

### 59. 如果 openGauss 向量库挂了怎么办？

> 向量检索是 RAG 管道的核心，挂了整个 QA 功能就不可用。但 openGauss 本身是分布式高可用的（主备+自动切换），向量库和 GaussMaster 复用同一套高可用体系。真的极端情况下，还有 Dynamic Config 所在的 SQLite 不受影响——至少配置还能读写。

### 60. 如果检索结果全是错的怎么办？

> 重排序的 score<0 过滤是第一道防线——负相关的直接丢弃。如果过滤后还是错的，LLM 推理阶段会再判断一次——prompt 模板里专门有指令让 LLM 判断"检索到的文档是否和问题相关"，不相关的话 LLM 会走搜索降级流程（HyDE+查询改写）。如果降级后还不行，返回"知识库中没有相关知识"。

### 61. 整个系统有没有健康检查机制？

> 启动时有全量连通性检查。运行时没有主动的定时健康检查——外部服务的可用性由银行运维平台监控，GaussMaster 不做重复工作。但每个请求失败时会触发 HTTP 层的重试机制。

## 十五、数据闭环与反馈

### 62. 用户反馈（点赞/点踩/举报）怎么用的？

> 存在 `qa_record` 表的 `like`/`hate`/`report_type` 字段。目前反馈数据主要用于：统计模型的回答质量、发现知识库的盲区（被点踩多的问题对应的文档可能缺失）、标记有争议的回答。但也说实话——目前反馈数据还没闭环到自动优化检索或微调模型，更多是人工定期复盘用。

### 63. 怎么发现知识库的盲区？

> 两个信号：一个是降级策略触发频率——如果某个方向的问题频繁走 HyDE/查询改写，说明现有知识库覆盖不足。另一个是用户点踩——被连续点踩的回答类型会被标记，定期人工补充相关文档。

### 64. 新版本 GaussDB 发布后，知识库怎么更新？

> 目前是离线手动更新——把新版本的文档重新做一遍"解析→分块→去重→向量化→入库"的流程。没有做增量更新——因为文档结构变化时，旧块和新块的 prev_uuid/next_uuid 链会断，增量更新容易产生断裂。全量重建大概需要几个小时，银行环境可接受。

## 十六、模型选型与评估

### 65. 为什么默认模型选盘古而不是 DeepSeek？

> 盘古是华为自研的，和 GaussDB 同属华为生态，内部部署和权限审批更方便。性能上，盘古 38B 在 GaussDB 领域的回答质量明显优于同级别的 DeepSeek-Chat。但我们的架构设计保证了模型可插拔——换模型只要改配置文件的 `api_type` 和 `api_url`。

### 66. 6 种模型你们怎么评估选哪个？

> 启动时 `get_all_available_online_llms()` 并行检测所有模型的连通性，能连通的标记为可用。默认用配置文件里 `model_name` 指定的，用户也可以在 API 参数里指定。前端有模型切换功能。

### 67. 有没有做过不同模型的 benchmark？

> 论文里有对比。在 400 多道银行真实问题上，盘古 71B > 盘古 38B > DeepSeek > ChatGLM3 > 百川 > Llama3。但论文侧重点是 GaussMaster 系统本身，不是模型 benchmark——我们更关注的是两阶段工具调用方案在不同模型上的准确率对比。

### 68. embedding 模型为什么不用 m3e 或者 text2vec？

> BGE 在 C-MTEB 中文基准上全面领先 m3e 和 text2vec。而且 BGE 社区活跃、文档齐全、微调教程成熟，银行内网部署有成熟方案。text2vec 虽然轻量但 768 维的判别力不如 BGE-large 的 1024 维。

## 十七、部署与运维

### 69. 银行内网环境具体怎么部署的？

> 纯离线环境，所有外部服务的 API URL 都指向内网地址。LLM（盘古 38B）部署在内网 GPU 集群上，embedding 和 reranker 也是内网独立服务。GaussMaster 本身是 Python 应用，通过 systemd 管理进程。前端 Vue.js 打包后由 Nginx 托管。

### 70. 日志和监控怎么做的？

> 日志用 Python logging，按 10MB 切分，保留 1 个备份。监控由银行运维平台统一做——GaussMaster 本身不重复造轮子。我们只暴露了健康检查端点给监控平台探测。

### 71. 配置文件里的密码怎么管理？

> 密码用 AES-256-CBC 加密存储。密钥分两部分——一部分在代码里，一部分在文件系统。即使单一泄露也无法解密。首次配置时明文写入，服务启动后自动加密替换。

## 十八、未来规划（展示视野）

### 72. 如果给你半年时间继续做，你会加什么？

> 三个方向。一是工具调用的自我进化——目前诊断树是专家手工定义的，理想情况是从工具调用历史里自动学习新的诊断路径。二是多模态——告警截图、执行计划可视化图片直接输入给 LLM 分析。三是主动式运维——不等用户问，系统自己定时巡检、发现异常主动推送诊断报告。

### 73. 你觉得 AI Ops 这个方向接下来最大的机会在哪？

> 从"被动问答"到"主动运维"。现在的 Copilot 还只是"用户问、系统答"，但真正的价值是系统在用户还没发现问题时就提前预警并给出修复方案。这需要把时序预测、异常检测、LLM 推理三类能力深度融合，也是我接下来想钻研的方向。
