# 向量化查询 vs 普通查询 — 全部表对照

## 有向量的表（语义搜索）

搜"意思相近"的，用 `<->` L2 距离操作符，走 GSDiskANN 索引加速。

| 表名 | 向量列 | 怎么搜 | 举例 |
|------|--------|--------|------|
| **gauss_kb** | `text_vector floatvector(1024)` | `<->` L2距离 + `###` BM25 双路混合 | "CPU飙高" 能匹配到 "处理器占用异常" |
| **custom_knowledge_{id}** | `text_vector floatvector(1024)` | 同上 | 用户自建知识库，搜法一样 |
| **case_op_kb** | `inspection_vector` | `<->` L2距离 | 搜历史故障案例 |
| **gm_tool_history_memory** | `question_vector floatvector(1024)` | `<->` L2距离 | "历史上有谁问过类似问题，当时调了什么工具" |

---

## 没向量的表（精确查询）

只能按字段精确匹配，用普通 SQL `WHERE`。

| 表名 | 所在库 | 连接方式 | 怎么搜 | 举例 |
|------|--------|---------|--------|------|
| **qa_record** | 向量库 | psycopg2 | `WHERE user_id=? AND session_id=?` | 查某个会话的 RAG 问答历史 |
| **knowledge_base** | 向量库 | psycopg2 | `WHERE user_id=?` | 查某用户创建了哪些知识库 |
| **data_source** | 向量库 | psycopg2 | `WHERE related_kb_id=?` | 查某个知识库上传了哪些文件 |
| **tb_interaction_memory** | MetaDatabase | SQLAlchemy | `WHERE user_id=? AND session_id=?` | 查某会话的 Agent 工具调用历史 |
| **tb_diagnostic_report** | MetaDatabase | SQLAlchemy | `WHERE report_id=?` | 查某个诊断报告 |
| **tb_managed_cluster** | MetaDatabase | SQLAlchemy | `WHERE host=? AND port=?` | 查注册的 openGauss 集群 |
| **dynamic_config** | 本地 SQLite | SQLAlchemy | key-value 查 | 读运行时配置、加密密钥 |

## 源码证据

# kb_config.py — vector_field 和 bm25_field 决定是否有向量能力

# ✅ 有向量 + 有 BM25
KT_TABLE_CONFIG = {
    "vector_field": ["text"],    # text 字段向量化
    "bm25_field": ["text"],      # text 字段 BM25 索引
    "text_field": ["uuid", "title", "text", ...]
}

# ✅ 有向量，没有 BM25
OPS_MEMORY_TABLE_CONFIG = {
    "GM_HISTORY_MEMORY": {
        "vector_field": ['question'],  # question 字段向量化
        "bm25_field": [],              # 没有 BM25
        ...
    }
}

# ❌ 既没向量也没 BM25
QA_TABLE_CONFIG = {
    "vector_field": [],    # 空
    "bm25_field": [],      # 空
    ...
}
KB_TABLE_CONFIG = {
    "vector_field": [],    # 空
    "bm25_field": [],      # 空
    ...
}
DS_TABLE_CONFIG = {
    "vector_field": [],    # 空
    "bm25_field": [],      # 空
    ...
}

## 为什么有的向量化有的没有

- **需要语义搜索的** → 向量化。比如知识文档（"CPU飙高"和"处理器占用异常"意思一样）、工具历史（"上次类似的故障"）
- **只需要精确匹配的** → 不向量化。比如按用户ID查历史、按知识库ID查文件列表。这些场景不需要"意思相近"，精确匹配就够了。向量化反而浪费存储和建索引时间。

---

## 向量检索的 SQL 长什么样

```sql
-- 向量检索（L2距离，GSDiskANN 加速）
SELECT * FROM gauss_kb
ORDER BY text_vector <-> '[0.12, -0.34, ..., 0.56]'
LIMIT 10;

-- BM25 全文检索
SELECT * FROM gauss_kb
ORDER BY text ### 'CPU 使用率飙高' DESC
LIMIT 10;
```

## 普通查询的 SQL 长什么样

```sql
-- qa_record：按用户+会话查历史
SELECT * FROM qa_record
WHERE user_id = 'zhangsan' AND session_id = 'sess_001'
ORDER BY create_time DESC
LIMIT 3;

-- knowledge_base：按用户查知识库列表
SELECT * FROM knowledge_base
WHERE user_id = 'zhangsan';

-- tb_interaction_memory：按用户+会话查工具调用历史
SELECT * FROM tb_interaction_memory
WHERE user_id = 'zhangsan' AND session_id = 'sess_001'
ORDER BY created_at DESC
LIMIT 3;
```
