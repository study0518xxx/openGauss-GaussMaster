# 11 - 内核项目衔接：怎么讲 openGauss 经历

## 一、面试官问内核的三个心态

1. **验证你四年没白过**——期待听到模块级别的深度，不是"修过几个 bug"
2. **判断你的工程素养**——内核开发是高质量代码的训练场，想确认你带了这种素养
3. **确认你是真想转，不是逃兵**——"为什么放弃内核"是必考题

---

## 二、5 道内核高频题

### Q1："你在内核主要负责什么？"

**别答**"慢 SQL 诊断、指标采集"——太抽象。

**要答成这样**：

> 主要负责查询诊断和可观测性相关的模块。具体三个方向：
>
> 一是慢 SQL 的诊断链路——从 pg_stat_activity 快照采集，到执行计划反解析，再到根因归类。以前 DBA 看慢 SQL 要手工 explain analyze，我们把这个过程自动化了，直接输出"统计信息过期导致 nest loop 选错"这种级别的结论。
>
> 二是指标采集框架。openGauss 的指标分散在几十张系统表和内存结构里，我重构了一版采集器，把采集延迟从秒级降到了毫秒级。
>
> 三是系统表的一些优化，比如 pg_stat_statements 的哈希表扩展策略调整。

三个效果：有模块（不是打杂）、有细节（毫秒级）、和 GaussMaster 有关联（慢 SQL → GaussMaster 的 slow_sql_rca 工具）。

### Q2："内核开发中最难的一个问题是什么？"

**他在乎你的解题思路，不在乎问题本身。**

准备一个具体 case，必须有：现象 → 排查过程 → 根因 → 修复方案。

**推荐案例**：

> 有一次线上偶发慢 SQL 的诊断结果和实际执行计划不一致。排查发现采集执行计划的时候，plan cache 已经被淘汰了，拿到的是 re-plan 后的新计划。
>
> 根因是采集器和 plan cache 淘汰之间存在竞态。解决方案不是加锁（会影响性能），而是改了采集时序——先拿 plan cache 的引用计数再读内容，读完之后释放引用。用引用计数替代锁，零性能损耗。

这个故事好在他能听懂（不需要内核背景也能理解竞态和引用计数的取舍），而且体现了工程思维（不暴力加锁而是用引用计数）。

### Q3："你是不是主要写 C？Python 写了多久？"

**他在丈量你的工程能力能不能覆盖 AI 应用开发。**

> 内核主力语言是 C，但 GaussMaster 整个项目是 Python 写的——FastAPI 的 web 层、Agent 的异步调用链、注册表的装饰器模式、inspect.signature 的参数校验，这些都是 Python。
>
> 而且内核开发里很多工具链本身就是 Python 写的，像代码生成、自动化测试框架，所以我写 Python 的时间其实比想象的长。不是"学了一周就开始写项目"的状态。

### Q4："为什么从内核转到 AI 应用？"

**这是全场最重要的问题。你不是逃兵，是增量更大。**

> 做 GaussMaster 的时候我发现：AI 应用最难的不是模型，是怎么把模型和已有的复杂系统可靠地接起来。
>
> 数据库内核我已经做了四年，接下来的成长曲线在放缓。但 AI 应用领域还非常早期，大部分做 AI 的人没有底层系统经验，做出来的东西经常在工程上站不住。我觉得这是我差异化最大的地方——我能把一个 AI 系统从头到尾踩实了落地。
>
> 不是觉得内核不好，是我在这个方向上能做出的增量更大。

### Q5："你觉得内核经验对 AI 应用开发有什么帮助？"

**这是他给你递话，让你展示优势。**

> 三个层面。
>
> **工程习惯上**，内核开发对正确性的要求是 100%——内存泄漏就是事故，并发竞争就是数据损坏。这种习惯带到 AI 应用里，天然会对 prompt 输出做确定性校验（用 inspect 而不是靠信仰）、对工具调用做多层 fallback。
>
> **系统感知上**，AI 应用最终还是要跑在真实系统上。GaussMaster 做慢 SQL 诊断的时候，我知道 pg_stat_activity 是快照、有采样窗口、某些状态可能漏掉。这些知识决定了工具接口怎么设计，LLM 是回答不出这些的。
>
> **性能敏感度上**，内核开发习惯了"这个操作是 O(n²) 的，数据量大了会炸"。这个思维在做 embedding 批处理、检索索引构建的时候直接复用。

## 三、他大概率不会问的

不要花时间准备这些，他不会问：

- B+tree 分裂的细节
- MVCC 的可见性判断算法
- WAL 日志的写入协议
- 分布式事务的 2PC 流程

他是面 AI 应用岗，不是面内核岗。问到"能判断你工程深度"的程度就停了。

```

· 负责查询诊断与可观测性模块，包括慢 SQL 诊断链路、指标采集框架及系统表优化
· 重构指标采集器架构，将采集延迟从秒级降至毫秒级
· 主导慢 SQL 根因自动归类方案，将人工分析耗时从平均 30 分钟压缩至秒级
```

三条刚好。第三条和 GaussMaster 的 `slow_sql_rca` 工具直接呼应——面试官看完两个项目会自然形成一条线："这个人从内核层一直做到了 AI 应用层。"
